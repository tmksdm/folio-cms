# ARCHITECTURE.md — Архитектура для ревью Stage 00

Статус: предложение, не утверждено. Проверяемые сведения и неопределённости: [исследование](docs/research/STAGE-00.md). Существенные изменения: [ADR-0001](docs/decisions/0001-static-cms.md).

## Минимальный стек и поток

Astro static, Markdown collections, обычный CSS, небольшой клиентский JS для темы и поиска, Pagefind после сборки, GitHub Actions для проверки и Pages. БД, production runtime, CMS-плагин, клиентский UI-framework и adapter не нужны. Node LTS и совместимые стабильные версии закрепить в Stage 01, вместе с lockfile и лицензиями. Сейчас зависимости не устанавливаются.

`src/content/articles/<slug>/index.md` и `images/` рядом → проверка исходников/реестра → только published collection → статический HTML → индекс Pagefind → проверка всего артефакта → Pages.

Обычный glob всех Markdown с фильтрацией только в getStaticPaths недостаточен для запрета draft media. До компиляции коллекции требуется отбор published (build-time loader или минимальное staging published дерева). Не вводить два источника истины: staging всегда временный. Окончательный способ выбрать в Stage 02 по тесту уникального draft изображения. Медиа вне public; public содержит только явно публичные системные файлы.

## Контент и идентичность

Обязательные поля: непустой `title`, строка `date` в кавычках (`YYYY-MM-DD`, реальная дата), `status: draft|published`, строка `slug` в кавычках. Не применять неявное Date coercion/UTC преобразование. Заголовок и body изменяемы; slug и дата после назначения фиксированы. Предлагаемый диапазон даты 2000–2099 исключает неоднозначность двухзначного года; это ограничение требует ревью.

```markdown
---
title: "Почему мозг нас обманывает"
date: "2026-10-11"
status: draft
slug: "261011"
---

![Иллюзия](./images/illusion.webp)
```

`slug` — сам ID; отдельный UUID не вводится. Файл обязан находиться в `<slug>/index.md`. Схема suffix: без suffix означает 1, далее целое N≥2 без ведущих нулей (`-1`, `-02`, `-0` запрещены). Порядок списка: date DESC, затем числовой N DESC. Имя collection entry не заменяет явный slug.

### Назначение и реестр

`content/slug-registry.json` — версия схемы и отображение `slug -> {date, state: active|retired}`; содержимое статей в реестре не дублировать. Имена записей пожизненно заняты, включая draft и retired. Каждый active имеет ровно один исходник с той же датой; каждый исходник имеет active запись. Retired не имеет исходника, его URL отвечает 404, переназначение запрещено. Восстановление той же статьи из backup допускается отдельным проверяемым исправлением, без смены slug/date.

CLI `new:article` получает дату и заголовок, вычисляет max N по полному реестру и исходникам, создаёт draft и запись одновременно в рабочем дереве. Нельзя считать количество статей или заполнять пробелы. Безопасная запись через временные файлы, отказ при занятом пути; ошибка не оставляет частичное состояние. CLI не пушит автоматически. Git является точкой сериализации, БД не нужна.

GitHub web: создать ветку, проверить реестр, выбрать следующий N, добавить запись и Markdown по шаблону в одном PR, загрузить локальные изображения, пройти validation и merge. В веб-редакторе нет автоматического атомарного распределителя ID: для автоматизации использовать локальный CLI. Workflow с ботом назначения ID отложен как лишняя сложность. Два параллельных PR могут выбрать один N; второй обновляется от main и получает новый ID до merge. Повторное назначение существующей статьи не разрешено.

Удаление: удалить исходник и отметить retired в одном изменении. Опубликованную статью можно вернуть в draft, резервирование сохраняется. Изменение даты требует нового draft с новым slug и явного решения о старом URL; не делать это скрыто. CI сравнивает реестр с базовым main для PR и предыдущим принятым состоянием для main: старые записи/даты не удаляются и не меняются, retired не оживает без отдельного review. Проверка одного snapshot не доказывает неизменность истории. В Stage 04 понадобится доступ к Git base и тест этой проверки; force push запрещён. CI не может определить семантическую подмену body — это предмет ревью.

## Маршруты и переносимость

Кандидат Astro: `output: 'static'`, `build.format: 'file'`, `trailingSlash: 'never'`. Статья `<slug>` → `dist/<slug>.html`, главная → `dist/index.html`. CMS не добавляет физический каталог base в dist. Служебная пагинация: `/page/2`, `/page/3` (первую страницу не дублировать).

Единая функция URL использует origin из `site` и нормализованный base (`''` или `/folio-cms`), а не `Astro.url.pathname` для canonical. Статьи, ссылки результатов поиска и canonical строго `<base>/<slug>`. Главная `<base>/` — допустимое исключение правила слеша для корня; Pages может перенаправлять `/folio-cms` на `/folio-cms/`. Base добавляется ровно один раз. Не предполагать, что ручной `/images/...` автоматически исправляется Astro.

Профили: project site `site=https://tmksdm.github.io`, `base=/folio-cms`; root/custom domain — соответствующий origin и пустой base. Нужна пересборка, контент и slug не меняются. Custom domain ещё не указан, DNS/CNAME не настраивать на Stage 00. На другом статическом хостинге требуется отдельно доказать extensionless mapping.

Обязательный gate Stage 04: реальный GET `<base>/261011` даёт HTTP 200 сразу, без HTTP/meta/JS redirect, финальный browser URL без `.html` и `/`, reload и no-JS работают. Astro preview не доказывает Pages. При провале прекратить deployment и вынести варианты заказчику: другие URL, другой статический хостинг или проверенный rewrite слой (последний меняет инфраструктурные ограничения). 404 SPA fallback и client redirect не выполняют gate.

## Markdown и медиа

Относительная Markdown image ссылка считается от исходного `index.md`, не от адреса страницы. Предпочтительны PNG/JPEG/WebP в локальном `images/`; Astro обрабатывает их на build-time. Проверить выбранный loader и base на fixture; документация не доказывает именно наш pipeline. Запретить traversal за разрешённое дерево и symlink наружу; missing asset блокирует build. Shared media разрешены только в явно выделенном локальном дереве с проверкой достижимости из published. Draft-only media не должны попасть в dist; общий файл, используемый published статьёй, публичен по определению.

Не использовать MDX. Raw HTML узлы Markdown отклонять с понятной ошибкой; fenced HTML остаётся текстом кода. Разрешать безопасные Markdown ссылки/изображения, отклонять `javascript:`, опасные data URLs и обработчики событий. Конкретный AST pipeline и тесты вводятся в Stage 02; не считать Astro sanitizer по умолчанию. Внешние HTTPS ссылки допустимы; локальные изображения — обязательная поддержка, CDN не нужен.

## Поиск

Stage 05: индексировать готовый HTML только опубликованных статей из списка маршрутов. `data-pagefind-body` охватывает заголовок и текст статьи, исключая дату/меню; `<html lang="ru">`. Не индексировать homepage, пагинацию, 404 и служебные файлы. Пустой корпус — пустой поиск, без перехода к индексации homepage.

Чтобы избежать `.html` в результатах, предпочтителен небольшой postbuild скрипт Pagefind Node API `addHTMLFile({url: '/<slug>', content: fullHtml})`. В index URL base не включать; search API `baseUrl` равен `<base>/`, import bundle — `<base>/pagefind/pagefind.js`. Проверить результат, отсутствие двойного base и ошибки каждой API операции. Альтернатива CLI — нормализация только проверенных внутренних article URL на границе UI, если тесты подтвердят контракт; не выбирать неявно.

Загрузка индекса по первому запросу/взаимодействию, без загрузки всех текстов на главной. Точное поведение prefix, morphology, `ё/е`, typo проверить на fixtures. Поиск целых русских слов — приёмочный критерий; произвольный substring/fuzzy не обещается. Ошибки fetch/WASM показывать по-русски; noscript объясняет необходимость JS.

## Deployment, UI, backup

PR workflow проверяет без deployment. Main/manual deploy: lockfile install → content/history validation → typecheck/tests → build → Pagefind (с Stage 05) → artifact audit → официальные Pages upload/deploy actions. Минимальные permissions, deployment concurrency, production deploy только принятых изменений. Не выполнять недоверенный PR с production secrets. Actions версии фиксировать и проверять в Stage 04.

UI — заголовки и даты, 20 на страницу, обычные ссылки; доступность, system/light/dark с localStorage fallback и ранним минимальным theme script. Stage 06 доводит тему, но draft gate обязателен с Stage 02.

Stage 07 ZIP — allowlist: Markdown (включая drafts), referenced local media, полный registry, публичная конфигурация, manifest версии/хешей, инструкция восстановления и ссылка на совместимый commit кода. Исключить `.git`, `.env`, credentials, node_modules, dist, caches. ZIP не заменяет offsite копию: Git history только в Git, архив требует отдельного хранения владельцем. Восстановление в чистый checkout того же toolchain, проверка хешей и нормализованных output маршрутов/контента/медиа (не timestamp ZIP). Статическая CMS достижима без БД; URL hosting gate остаётся недоказанным.
