# Архитектура

## Stage 01: собственный email-вход

Один Cloudflare Worker, обычные HTML/CSS/JavaScript, без клиентского фреймворка. HTML и ресурсы включены в bundle. Cloudflare Access / Zero Trust не используются: по подтверждённому заданию `05.txt` они заменены Resend и Turnstile.

Браузер → публичная `/login` → серверная проверка Turnstile → Resend → шестизначный код → cookie-сессия → защищённая админка. Форма входа не спрашивает email: единственный получатель задан серверным ALLOWED_EMAIL, адрес из браузера не принимается и на странице входа не показывается. Отправитель — `Folio <onboarding@resend.dev>`; в этом режиме Resend разрешает доставку только владельцу своего аккаунта. Без собственного домена это ограничение подходит только личной панели.

Публичны только GET/HEAD `/login`, `/assets/login.css`, `/assets/login.js` и POST `/auth/request`, `/auth/verify`, `/auth/logout`. Все остальные страницы, ресурсы, API и неизвестные пути проверяют серверную сессию до маршрутизации. Анонимные `/`, `/sites`, `/settings` перенаправляются на вход; ресурсы/API возвращают 401. Заголовки Access и email не дают доступа. Нет конфигурации/хранилища → 503; неверный origin → 403. Все ответы no-store; CSP разрешает внешние скрипт/iframe Turnstile только на странице входа.

## Атомарность и ограничения

Один Durable Object `owner-auth-v1`, SQLite backend (`new_sqlite_classes`), одна строка состояния. Это минимальное хранилище авторизации, а не БД контента CMS. Workers KV не применяется из-за eventual consistency. SQLite Durable Objects доступны на Workers Free: [тариф и квоты](https://developers.cloudflare.com/durable-objects/platform/pricing/). На Free превышение квот приводит к отказам, а не автоматическому переходу на платный план.

`storage.transactionSync` атомарно читает, проверяет и записывает состояние. Внешние запросы выполняются вне транзакций. До отправки письма сохраняются квота и неподтверждённый код; только успешный ответ Resend активирует код. Неуспешная/неопределённая отправка расходует лимит и не разрешает вход. Поздний ответ старой отправки не активирует заменённый код. Состояние и квоты переживают перезапуск объекта.

- Случайный код: 6 цифр, Web Crypto без modulo bias; срок 10 минут от резервирования. Новая отправка заменяет предыдущий код.
- Код привязан к cookie браузера `__Host-folio-challenge` (256 бит). Без совпадения cookie чужой браузер не расходует попытки текущего кода.
- Максимум 5 попыток на код, дополнительно 30 попыток за скользящий час. Проверка, расход попытки, удаление кода и создание сессии — одна транзакция. Конкурентно код используется ровно один раз.
- Отправки: минимум 60 секунд между ними, максимум 5 за скользящий час и 20 за скользящие сутки. Эти лимиты общие для владельца, независимо от IP/браузера, и включают неудачные отправки.
- До Siteverify: максимум 30 непустых запросов в минуту с одного доверенного `CF-Connecting-IP`. IP хранится как SHA-256, счётчики живут минуту, максимум 256 активных IP. При заполнении новые IP временно получают 429. Нет доверия `X-Forwarded-For`.
- Siteverify проверяет success, точный hostname APP_ORIGIN и action `login`. Токены Turnstile одноразовые; отказ/таймаут не разрешает отправку. [Серверная проверка](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).
- POST требует точный Origin, JSON и тело до 4096 байт; cross-site/same-site Fetch Metadata отклоняются. Сервер принимает запросы только на APP_ORIGIN.

Сессия: случайный токен 256 бит, сервер хранит только SHA-256; cookie `__Host-folio-session`, Path=/, HttpOnly, Secure, SameSite=Strict, без Domain. Абсолютный срок — 1 час, без автоматического продления; максимум 10 активных сессий (самая старая вытесняется). Выход — POST с проверкой Origin, удаление серверной сессии и обеих cookies. Изменение AUTH_SECRET, разрешённого email или APP_ORIGIN отзывает прежние коды/сессии. Коды хранятся как HMAC-SHA256 с серверным секретом; plaintext существует только в памяти на время отправки.

Лимиты защищают почтовую квоту и перебор, но не гарантируют доступность против распределённого DDoS и исчерпания бесплатных квот. Любой анонимный посетитель, прошедший Turnstile, расходует общую квоту отправок — письмо всегда уходит на ALLOWED_EMAIL. Это следствие входа без ввода email и ограничение личного входа, без обещаний неуязвимости.

## Файлы и проверки

`src/auth.js` — конфигурация, криптография, cookies, обращение к фиксированному объекту; `src/auth-store.js` — код, лимиты, Resend, Turnstile и сессии; `src/worker.js` — маршруты/защита; `src/login.js` — вход; `src/ui.js` — прежняя админка и выход.

Секреты AUTH_SECRET, RESEND_API_KEY, TURNSTILE_SECRET_KEY и приватный ALLOWED_EMAIL — Worker secrets. APP_ORIGIN и публичный TURNSTILE_SITE_KEY тоже задаются через secrets ради единого способа настройки; только sitekey включается в страницу входа. Не хранить значения в Git/логах. Observability выключена, код не логирует тела, email, токены и ответы upstream.

`tests/worker.test.js` использует настоящую SQLite и криптографию с управляемыми часами и внешней сетью. `tests/runtime.test.js` запускает production-модули в workerd с SQLite Durable Object. `tests/preview-server.js` — только HTTPS localhost с временным состоянием и подменой доставки/CAPTCHA; `/__test/code` существует исключительно в тестовом entrypoint, отсутствует в production. Подмена внешнего виджета в браузерном сценарии не доказывает реальный Turnstile.

### Уровни доказательств

Утверждения ниже помечены одним из трёх уровней; смешивать их нельзя.

- **[П]** — проверено непосредственно на живом GitHub в эксперименте 2026-10-13: прямые ответы API и сервиса.
- **[И]** — наше HTTP-измерение (статус, `Location`, `Content-Type`, поведение браузера); независимым ревьюером не проверялось.
- **[Д]** — предполагается по документации GitHub; на живом аккаунте `tmksdm` не проверялось.

### Авторизация GitHub: вариант D отклонён измерением, рекомендуется вариант A

Изначально был выбран вариант **D** (installation-токен для всех вызовов, включая создание репозитория). Живой эксперимент 2026-10-13 показал, что на личном аккаунте `tmksdm` он **не выполняется полностью** [П]: installation-токен делает всё, кроме создания репозитория. Поэтому «выбранного варианта D» больше нет — для цели «создать сайт без ручных действий владельца» он неработоспособен. Рекомендация — вариант **A** (installation-токен для управления, user access token приложения только для создания репозитория); обоснование и недоказанные предпосылки — в конце раздела.

**Проверено на живом аккаунте `tmksdm` 2026-10-13.** Приложение `folio-cms-pages` (App ID 5299581) установлено на `tmksdm` (установка `170953323`, `repository_selection: all`), выданные права — `administration: write`, `contents: write`, `pages: write`, `metadata: read` [П]. Installation-токен на этом аккаунте работает для всего, кроме создания репозитория:

- создание файлов и коммитов: `PUT /repos/.../contents/folio.json` → `201`; Git Data API (blobs → trees → commits → refs) → `201`/`200` [П];
- включение Pages: `POST /repos/.../pages` → `201` (`build_type: legacy`, `https_enforced: true`), `GET /repos/.../pages` → `200`, `GET /repos/.../pages/builds` → `200` [П];
- видимость репозиториев: `GET /installation/repositories?per_page=100` вернул 41 из 41, включая созданный в ходе эксперимента [П];
- **`POST /user/repos` → `403`** с телом `{"message":"Rate Limit Exceeded"}` [П]. Воспроизводимо: три попытки с интервалами 90 секунд дали тот же ответ. Сохранённые заголовки ответа: `x-ratelimit-limit: 6000`, `x-ratelimit-remaining: 5992` (первичный лимит не исчерпан), `x-accepted-github-permissions: administration=write; repository_creation=write` (право считается принятым). Тот же вызов user-токеном `gh` (scope `repo`) в тот же момент создал репозиторий (`201`) [П].

**Причина `403` не установлена.** Остаток первичного лимита (`5992` из `6000`) не исключает secondary rate limiting, abuse detection и других серверных ограничений GitHub: сообщение `Rate Limit Exceeded` покрывает их все и не различает. Достоверно установлено только эмпирическое правило: этим приложением на этом аккаунте installation-токен не создаёт репозиторий user-владельца, тогда как user-токен `gh` создаёт.

Безопасные диагностические сведения, которых **не хватает** для различения причин: наличие и значение `retry-after`; `documentation_url`, `x-github-request-id` и полное тело ответа (в отчёте они не сохранены); поведение того же вызова с заведомо невалидным телом (отличает «нет права на endpoint» от «сплошной отказ»); поведение после ожидания окна `x-ratelimit-reset`. Повторять создание репозиториев для диагностики сейчас не требуется — минимальные проверки перечислены в разделе «Рекомендация: вариант A».

Документация обещала, что installation-токен этот вызов поддерживает [Д], и это тот случай, когда контракт разошёлся с наблюдением:

- В справочнике прав (машиночитаемые данные страницы) запись этого вызова: `{"slug":"create-a-repository-for-the-authenticated-user","verb":"post","requestPath":"/user/repos","access":"write","user-to-server":true,"server-to-server":true}`. `server-to-server: true` — это и есть installation access token; для сравнения, `GET /user/repos` там же имеет `server-to-server: false`.
- На странице endpoint'а блок «Fine-grained access tokens for "Create a repository for the authenticated user"» содержит ссылку **GitHub App installation access tokens** (рядом с user access tokens и fine-grained PAT) и набор прав «Administration» (write) либо «Repository creation» (write).

Документация — это контракт, а не наблюдение за работой API [Д]. Наблюдение [П] ему противоречит: installation-токен репозиторий создать не смог, хотя для всех остальных вызовов работает.

Запасной вариант **A** и есть рекомендация плана: installation-токен работает для управления (файлы, темы, Pages, статус), а создание репозитория выполняет user access token того же приложения; это единственное место, где нужен второй токен. **Важно:** в эксперименте репозиторий создал user OAuth-токен `gh` — это другой тип токена и другая выдача, а не user access token приложения [П]. Поэтому работоспособность варианта A **не доказана**: подтверждено лишь то, что user-токен вообще может создать репозиторий в этом аккаунте. Полный цикл (браузерная авторизация владельцем → user access token приложения → создание репозитория → обновление пары токенов) не проверялся. Второй вариант, не требующий второго токена, — оставить создание репозитория владельцу (одно действие в веб-интерфейсе на сайт), что противоречит цели «создание сайта с телефона без ручных действий».

| Вариант | Создание репозитория в личном аккаунте | Автоматическое обновление | Секреты в Worker | Хранимое состояние | Сложность |
|---|---|---|---|---|---|
| D. installation-токен для всех вызовов (был выбран, **отклонён измерением** [П]) | **нет**: `403 Rate Limit Exceeded` при выданном `Administration` (write) и неизрасходованном первичном лимите; причина не установлена | да: JWT (≤10 мин) → токен на 1 час, при каждом промахе кэша выпускается новый | App ID, приватный ключ, owner | нет | минимальная, но для цели неработоспособна |
| **A. user-токен для создания, installation для остального (рекомендуется)** | для токена приложения **не проверено** [Д]: репозиторий создал user OAuth-токен `gh` (`201`) [П], а не user access token приложения | да, но только если включено истечение и настроен refresh: токен 8 ч, refresh 6 мес, одноразовая ротация | App ID, ключ, owner, client ID, client secret | долгоживущий refresh-токен (ротация) → нужна запись в Durable Object | средняя |
| B. user-токен для всех вызовов | то же, что A, для всех вызовов | то же | то же | то же | средняя |
| C. fine-grained PAT | по документации да (fine-grained PAT в списке для того же endpoint'а) [Д] | нет: токен статичный (бессрочный допустим, по умолчанию 30 дней) | один PAT | нет | низкая, но долгоживущий bearer-секрет |

Дополнительно по вариантам A и B: user access token по умолчанию живёт 8 часов, refresh-токен — 6 месяцев и одноразовый (каждое обновление выдаёт новый, старый перестаёт действовать), то есть ротация требует постоянного хранения последнего refresh-токена. Истечение user-токенов — включаемая опция приложения: если её отключить, токен не истекает и обновление не нужно, но тогда это долгоживущий секрет, что противоречит минимальным правам. Оба варианта требуют разовой браузерной авторизации владельцем (device flow или установка с запросом user-авторизации) и двух дополнительных секретов. По варианту C: бессрочный fine-grained PAT технически допустим, GitHub удаляет PAT, не использованные год; покрывает ли его выбор «All repositories» новые репозитории, документацией для нас не подтверждено — это тоже вопрос предварительной проверки.

Что произойдёт при истечении или отзыве:

- **D**: installation-токен истекает через час — это норма, новый выпускается автоматически; ключ приложения отозван или удалён — `github_auth_failed` с инструкцией загрузить новый ключ; установка снята — `installation_missing`; ничего не «залипает», владелец повторяет установку один раз.
- **A/B**: истёк refresh-токен (6 месяцев без использования), отозвана авторизация или изменён client secret — Folio сообщает «требуется повторная авторизация» и показывает ссылку; без однократного действия владельца создание сайтов не работает.
- **C**: PAT истёк, отозван или удалён за неиспользование — замена секрета вручную.

**Права по вызовам** (installation-токеном, кроме JWT-вызовов и создания репозитория — оно уходит user access token'у приложения):

| Вызов | Токен | Требуемое право |
|---|---|---|
| `GET /app/installations` | JWT приложения | — |
| `POST /app/installations/{id}/access_tokens` | JWT приложения | — |
| `GET /installation/repositories` | installation | `Metadata` (read) |
| `GET /repos/{owner}/{repo}` | installation | `Metadata` (read) |
| `POST /user/repos` | **user access token приложения** (installation-токен [П] отклонён `403`; причина не установлена) | по документации `Administration` (write) либо `Repository creation` (write) [Д]; в отчёте право числилось принятым, но вызов отклонён |
| `GET`/`PUT` `/repos/{owner}/{repo}/contents/{path}` | installation | `Contents` (write) |
| `PUT /repos/{owner}/{repo}/topics` | installation | `Administration` (write) |
| `GET`/`POST` `/repos/{owner}/{repo}/pages` | installation | `Pages` (write) + `Administration` (write) |
| `GET /repos/{owner}/{repo}/pages/builds/latest` | installation | `Pages` (read) |
| `POST /repos/{owner}/{repo}/pages/builds` | installation | `Pages` (write) |

Итоговый набор прав приложения: `Administration` (write), `Pages` (write), `Contents` (write), `Metadata` (read). Право `Workflows` не запрашивается: каталог `.github/workflows` Folio не трогает, а без этого права GitHub отклоняет запись в него (документация Contents API). Источники: [Create a repository for the authenticated user](https://docs.github.com/en/rest/repos/repos#create-a-repository-for-the-authenticated-user), [Create a GitHub Pages site](https://docs.github.com/en/rest/pages/pages#create-a-github-pages-site), [права приложений](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps), [user-токены](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app), [обновление user-токенов](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens), [fine-grained PAT](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens).

**Минимально необходимый набор прав.** `Metadata` (read) — обязательное, выдаётся всегда. `Contents` (write) — запись `folio.json`, `index.html`, `.nojekyll` и статей. `Pages` (write) — включение и чтение Pages и сборок. `Administration` (write) — темы репозитория (`PUT /topics`) и включение Pages [Д]; это самое широкое право (настройки, доступы, удаление репозитория), и именно оно повышает цену ошибки. Право `Workflows` не запрашивается: каталог `.github/workflows` Folio не трогает. Расширять набор без измерения, показывающего необходимость, не нужно.

**Риск установки `All repositories`.** `repository_selection: all` даёт приложению доступ на чтение и запись ко всем репозиториям аккаунта (в измерении — 41 из 41), включая будущие; при утечке приватного ключа или ошибке в коде цена ошибки — весь аккаунт. Более узкий режим (`selected` со списком) уменьшил бы область, но тогда новые репозитории в неё автоматически не попадают, а добавить их в `selected`-установку без user-токена нельзя — это ломает цель автоматизации. Поэтому выбран `all`; компенсации — ключ хранится только как Worker secret (PKCS#8), секреты не логируются, право `Workflows` не выдаётся, эксперименты идут на отдельном пробном репозитории.

JWT и токен: подпись `RS256`, claim'ы `iss` = App ID, `iat` на 60 секунд назад, `exp` не более 10 минут; далее `POST /app/installations/{id}/access_tokens` → installation-токен на час. Наблюдённый лимит установки 2026-10-13 — 6 000 запросов в час (`x-ratelimit-limit: 6000`), а не 5 000, как предполагалось. Ключ, скачанный из интерфейса приложения 2026-10-13, — PEM `PKCS#1 RSAPrivateKey`, RSA 2048 (пункт «Credentials → Key pairs → New key»; раздел «Private keys» в текущем интерфейсе отсутствует), а WebCrypto принимает только `PKCS#8`: конвертация `openssl pkcs8 -topk8 -inform PEM -outform PEM -nocrypt -in key.pem -out key-pkcs8.key` остаётся обязательной для Worker. Подпись RS256 и импорт `pkcs8` в Workers поддержаны ([Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/)).

Секреты: `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY` (PKCS#8), `GITHUB_OWNER` — логин аккаунта, которому принадлежат сайты (используется для выбора установки, построения адреса `https://<owner>.github.io/<name>` и запрета любых действий в чужом аккаунте). Рекомендуемый вариант A добавляет `GITHUB_CLIENT_ID` и `GITHUB_CLIENT_SECRET`.

Выбор установки: `GET /app/installations` возвращает установки с объектом `account`; берётся та, у которой `account.login` совпадает с `GITHUB_OWNER`. Ни одной → `installation_missing` (503 с инструкцией установить приложение). Несколько подходящих → `installation_ambiguous` (ошибка конфигурации; Folio не угадывает). Ответы GitHub отображаются на ошибки: `401` → `github_auth_failed`, `403`/`404` по конкретному репозиторию → `repository_access_denied`, `403` по лимиту → `rate_limited` со временем сброса.

Новые репозитории и область доступа: документацией не подтверждено, что созданный приложением репозиторий сразу попадает в установку с доступом «All repositories». Folio на это не полагается — сразу после создания репозиторий перечитывается тем же installation-токеном, и при `403`/`404` выводится «приложение не имеет доступа к новому репозиторию: переустановите его с доступом ко всем репозиториям», сайт остаётся незавершённым и доводится до конца повтором. Выдать себе доступ Folio не может: `PUT /user/installations/{id}/repositories/{repo_id}` требует пользовательского токена с правами администратора, а не installation-токена.

Пагинация: `GET /installation/repositories?per_page=100&page=N`; в ответе `total_count`, `repositories`, `repository_selection`. Страницы читаются до `total_count` с жёстким пределом (5 страниц); превышение — явная ошибка, а не молчаливое усечение списка. `repository_selection: selected` показывается предупреждением: при выборочном доступе новые сайты могут быть недоступны приложению.

### Принадлежность репозитория: доказательство только `folio.json`

Текстовые признаки (`description`, тема) владелец может изменить вручную, поэтому доказательством они не считаются.

| Признак | Роль | Даёт право записи |
|---|---|---|
| `folio.json` в корне: `{"managedBy":"folio-cms","site":"<256-бит id>","version":1,"title":"…"}` | единственное доказательство, что репозиторий ведёт Folio | да, автоматически |
| Описание `Folio site: …` | подсказка человеку и признак незавершённого создания | нет |
| Тема `folio-site` | дешёвый фильтр для списка | нет |

Правила:

- **Проверенный** — есть `folio.json` с корректной структурой, `managedBy` и непустым `site`. Разрешены досоздание и будущие операции; существующие файлы всё равно не перезаписываются.
- **Неподтверждённый** — репозиторий есть, `folio.json` отсутствует или повреждён. Автоматических записей нет: в админке он показывается как «требует подтверждения», и только явное действие владельца («Это репозиторий Folio — продолжить») разрешает записать **один** файл `folio.json`. Дальше сайт становится проверенным. Подтверждение — параметр запроса, а не хранимое состояние: если владелец закроет браузер, он подтвердит повторно.
- **Чужой** — ни `folio.json`, ни подтверждения: Folio не пишет ничего и отвечает `name_taken`.
- Имена `<owner>.github.io` (пользовательский сайт аккаунта) и `folio-cms` (движок) не трогаются никогда, даже при подтверждении.
- Существующие файлы не перезаписываются ни при каких условиях в Stage 02; записываются только отсутствующие.

Почему так безопасно и почему не нужна база: окно между созданием репозитория и записью `folio.json` — секунды, и внутри него Folio не угадывает, а спрашивает. Случайное подтверждение маловероятно, потому что репозиторий принадлежит владельцу и в области доступа установки находятся только его репозитории. Отдельное хранилище для этой задачи не нужно: подтверждение приходит из интерфейса, а незавершённое состояние выводится из GitHub.

Рассмотрена и отклонена более тяжёлая альтернатива: создание репозитория из template-репозитория (`POST /repos/{template_owner}/{template_repo}/generate`) даёт репозиторий сразу с содержимым и убирает окно совсем, но требует постоянного публичного репозитория-шаблона, замораживает содержимое сайта и всё равно нуждается во втором шаге для уникального `site` id. Проще спросить один раз.

Список сайтов строится из репозиториев установки с темой `folio-site` (дешёвый фильтр), и в списке показываются только те, у кого `folio.json` проверен; остальные — «требует внимания» без права записи. Если тему у сайта снимут вручную, он пропадёт из списка; вернуть его можно, введя имя в админке — Folio прочитает `folio.json` и, если он корректен, покажет сайт снова.

### Создание сайта: сходимость вместо «идемпотентности из коробки»

Каждый шаг — «прочитать, затем дописать», для имени `name`:

1. `GET /repos/{owner}/{name}`: нет репозитория → создавать; есть и он проверенный или явно подтверждённый → досоздавать; иначе → `name_taken`/`unconfirmed`, ничего не менять.
2. `POST /user/repos {name, private:false, auto_init:true, description:"Folio site: …", homepage}` — **user access token приложения** (installation-токен здесь отклонён [П]); остальные шаги — installation-токеном. `201` → дальше; `422` → перечитать и применить правила принадлежности (гонка); таймаут/`5xx` → перечитать: репозиторий есть и он проверенный или подтверждённый → дальше, иначе явная ошибка шага.
3. Файлы, в порядке `folio.json`, `index.html`, `.nojekyll`: только отсутствующие. `GET /contents/{path}` → `404` → `PUT`; `409`/`422` про `sha` → перечитать и сравнить содержимое: совпало → шаг выполнен, отличается → отказ с требованием подтверждения.
4. Тема: `GET /topics` → объединение с `folio-site` → `PUT` (endpoint заменяет набор целиком, чужие темы сохраняются).
5. Pages: `GET /pages`; `404` → `POST` `{build_type:"legacy", source:{branch:"main", path:"/"}}`; `200` → уже настроено, настройки владельца не меняются (в том числе не переводим `workflow` на `legacy`).
6. Ответ содержит фактическое состояние: репозиторий, файлы, тема, Pages (`status`, `html_url`). Сборка не ожидается.

Гарантируется: второй репозиторий для одного имени не создаётся; существующие файлы не перезаписываются; чужие репозитории не изменяются; повтор приводит систему к одному и тому же состоянию; одновременные запросы на одно имя безопасны (единственная неидемпотентная операция — создание репозитория, и её гонка закрыта перечитыванием с проверкой принадлежности).

Намеренно не обещается: ровно однократное выполнение шагов (лишних коммитов нет, потому что существующие файлы не переписываются); откат созданного репозитория; удаление «осиротевшего» репозитория из интерфейса — при сбое он остаётся, досоздаётся повтором или подтверждением, а удалить его можно вручную в GitHub.

Сценарии для тестов: репозиторий создан, `folio.json` ещё не записан (подтверждение и досоздание); файлы записаны, тема или Pages — нет; GitHub выполнил операцию, а Worker получил таймаут; два одновременных запроса на одно имя; браузер закрыт и запрос повторён позже; имя занято чужим репозиторием; повреждённый `folio.json`; недоступный приложению репозиторий.

### Публикация Pages

Настройка: `build_type: "legacy"` и `source: {branch:"main", path:"/"}` — сборка из ветки, без workflow-файлов и без права `Workflows`. `.nojekyll` записывается до включения Pages; GitHub описывает этот файл как признак того, что ветка не требует шага сборки, а не как гарантию поведения — поэтому в эксперименте (шаг 1) сборка проверяется и с файлом, и без него. Проверено 2026-10-13 [П]: `POST /repos/.../pages` вернул `201` с `build_type: legacy` и `https_enforced: true`, а первая сборка после включения Pages завершилась `errored` («Page build failed.»), последующие — `built` за 3–44 с. Единичный сбой ранней сборки наблюдён на живом репозитории, поэтому интерфейсу нужен повтор проверки, а не вывод «сайт сломан».

«Pages настроены» и «сайт доступен» — разные состояния. Первое: `GET /repos/{owner}/{repo}/pages` вернул сайт со `status`. Второе: реальный `GET https://<owner>.github.io/<name>/` из Worker со статусом `200` и меткой страницы `<meta name="folio-site" content="<name>">`. В интерфейсе это «публикуется» и «опубликован».

`status: building` — нормальное состояние: проверка повторяется отдельными запросами (`GET /api/sites/<name>/status`), без ожидания внутри запроса создания. `errored` — показывается `error` из `GET /pages/builds/latest` и предлагается повтор сборки (`POST /pages/builds`; на репозиторий допускается одна сборка одновременно). Недоступность GitHub в момент проверки — не «сайт сломан», а «статус неизвестен, проверьте снова».

Ограничение времени в Worker: на Free это 10 мс CPU на запрос, ожидание сети в CPU не считается — ограничивают число подзапросов (50 на запрос на Free) и терпение клиента. Поэтому каждый вызов GitHub идёт с `AbortSignal.timeout(8000)` (как в Stage 01), запрос создания делает не более ~12 подзапросов и никогда не ждёт сборку, а статус публикации проверяется отдельными вызовами. Исчерпание бюджета — ошибка «не завершено, повторите»; повтор безопасен. [Лимиты Workers](https://developers.cloudflare.com/workers/platform/limits/).

### Адреса статей: требование выполнимо статическим файлом `YYMMDD.html`

Требование владельца — `/site-name/YYMMDD` без `.html` и без завершающего слеша — **выполняется**, и Jekyll для этого не нужен. Измерено 2026-10-13 [И] на живом репозитории `tmksdm/folio-pages-probe` (`https://tmksdm.github.io/folio-pages-probe/`) в состоянии, в котором будет работать Folio: записан `.nojekyll`, статьи — статические файлы, `YYMMDD.html` лежит в корне.

| Адрес | HTTP | `Location` | `Content-Type` | Итог |
|---|---|---|---|---|
| `/YYMMDD` (файл `YYMMDD.html`) | `200` | — | `text/html; charset=utf-8` | **требование выполнено**; в браузере адресная строка остаётся `/folio-pages-probe/261013` |
| `/YYMMDD.html` | `200` | — | `text/html; charset=utf-8` | прямая ссылка на тот же файл |
| `/YYMMDD/` | `404` | — | `text/html; charset=utf-8` | каталога нет, существует только файл |
| `/b` при файле `b.html` | `200` | — | `text/html; charset=utf-8` | подтверждает подстановку расширения |
| `/a` при файле `a/index.html` | `301` | `…/a/` | `text/html` | каталог без слеша переадресуется — не годится |
| `/c` — файл без расширения | `200` | — | `application/octet-stream` | браузер скачивает файл, переход прерывается (`ERR_FAILED`) — не годится |
| `/_redirects` | `200` | — | `application/octet-stream` | файл отдаётся как есть; правил переадресации GitHub Pages не применяет |
| несуществующий путь | `404` | — | `text/html; charset=utf-8` | тело ответа берётся из `404.html` (только измерение, механизмом публикации не является) |

Тот же репозиторий в режиме Jekyll — посты с именами вида `YYYY-MM-DD-slug.md` и явным `permalink: /261013`:

| Адрес | HTTP | `Content-Type` |
|---|---|---|
| `/261013` (Jekyll permalink) | `200` | `text/html; charset=utf-8` |
| `/261013/` | `404` | `text/html` |
| `/2026/10/13/default.html` (permalink по умолчанию) | `200` | `text/html` |
| `/_redirects` | `404` | `text/html` |

Что из этого следует:

- Простейшая форма — статический файл `YYMMDD.html`, а ссылки ведут на `/YYMMDD`. Jekyll, `_redirects` и согласование `Accept` для этого не нужны. Вариант `YYMMDD/index.html` отпадает из-за `301`, вариант файла без расширения — из-за `application/octet-stream`: браузер скачивает его вместо показа.
- Запрос без расширения работает и с `.nojekyll`, и без него: подстановка `.html` от Jekyll не зависит. Но без `.nojekyll` Jekyll обрабатывает репозиторий и не публикует файлы и каталоги с `_` в начале, поэтому `.nojekyll` записывается всегда.
- Jekyll принимает посты только с именем `YYYY-MM-DD-slug.md`: файл `261013-probe.md` он игнорирует молча, и адрес `/261013` отдаёт `404`. Это наблюдённый отказ, а не предположение; для статической публикации он несущественен.
- `_redirects` (возможность Cloudflare Pages) на GitHub Pages не поддерживается.
- Согласование по `Accept: text/html` не изменило ни один статус и ни один `Content-Type`.

Схема публикации — **статический файл `YYMMDD.html` плюс `.nojekyll`** — успешно измеренный кандидат [И], сохраняющий точное требование владельца: `/YYMMDD` без `.html`, без завершающего слеша и без перенаправления. Требование к адресам не меняется. Второй материал того же дня (`YYMMDD-2.html`, ссылка `/YYMMDD-2`) по ожидаемому механизму адресуется так же, но это **отдельный пункт проверки Stage 03**: измерением шага 1 он не подтверждён.

### Список сайтов, независимость, телефон

Список сайтов — репозитории установки с темой `folio-site`, у которых проверен `folio.json`; состояние публикации и доступность проверяются отдельно. Своего хранилища нет: метаданные — в репозитории, `folio.json` — источник заголовка и настроек. Единственный Durable Object `owner-auth-v1` остаётся хранилищем авторизации; новых binding и постоянного кэша не добавляется (installation-токен кэшируется в памяти изолята не дольше часа).

Независимость: у каждого сайта свой репозиторий, история, Pages-сайт и адрес. Folio не пишет общие файлы, поэтому поломка или удаление одного сайта не затрагивает другие и сам `tmksdm/folio-cms`.

Телефон: форма имени и заголовка с крупными целями, нормализация имени (нижний регистр, пробелы в дефисы), инлайн-проверка, состояния «создаётся», «публикуется», «опубликован» с кнопкой «проверить снова», подтверждение для неподтверждённого репозитория, повтор при сбое, ссылка на сайт.

### Рекомендация: вариант A для автоматического создания сайтов

Рекомендуется вариант **A**, потому что он единственный сохраняет цель «создать сайт с телефона без ручных действий владельца» и опирается на уже измеренные операции:

- installation-токен — всё управление: `GET /installation/repositories`, запись файлов и коммиты, темы, включение Pages, чтение статуса [П];
- user access token приложения (user-to-server) — только `POST /user/repos`; получается браузерной авторизацией приложения владельцем, refresh-токен хранится в Durable Object с одноразовой ротацией.

Дополнительные секреты: `GITHUB_CLIENT_ID` и `GITHUB_CLIENT_SECRET` (плюс уже названные App ID, ключ PKCS#8, owner).

**Недоказанные предпосылки (все — [Д], на живом аккаунте не проверены):**

1. GitHub App **user access token** умеет создавать репозитории в личном аккаунте. Для **user OAuth-токена `gh`** измерено обратное — он создаёт [П], но это другой тип токена и другая выдача, поэтому переносить результат на токен приложения нельзя.
2. Полный цикл браузерной авторизации приложения владельцем (выдача user-токена) на живом аккаунте не выполнялся.
3. Обновление user-токена (refresh, срок 6 месяцев, одноразовая ротация) и его хранение в Durable Object не проверялись.
4. Причина `403` у installation-токена не установлена, поэтому нельзя утверждать, что дело именно в типе токена как таковом.

**Минимальная проверка без создания дополнительных репозиториев:**

- Действие владельца не нужно: повторить `POST /user/repos` installation-токеном с **заведомо невалидным** телом (например, `{"name":""}` или имя с недопустимым символом). Такой запрос ничего не создаёт. Ответ `422` означает, что токен доходит до endpoint'а и отклонение было ресурсным/лимитным; повторный `403` означает более ранний отказ. Это уточняет причину `403`, не создавая репозиториев.
- После отдельного разрешения владельца: выдать user access token приложения через OAuth (одно браузерное действие) и проверить его возможности **без создания репозитория** — `GET /user` (идентичность) и `x-oauth-scopes`; затем `POST /user/repos` с уже занятым или недопустимым именем: разрешённому токену GitHub отвечает ошибкой валидации, а не `403`.
- Проверить ротацию refresh-токена (обмен без создания репозиториев).
- Только после этого — один пробный репозиторий user access token'ом приложения; это снова требует явного разрешения владельца.
