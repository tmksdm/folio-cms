# Архитектура

## Stage 01: собственный email-вход

Один Cloudflare Worker, обычные HTML/CSS/JavaScript, без клиентского фреймворка. HTML и ресурсы включены в bundle. Cloudflare Access / Zero Trust не используются: по подтверждённому заданию `05.txt` они заменены Resend и Turnstile.

Браузер → публичная `/login` → серверная проверка Turnstile → Resend → шестизначный код → cookie-сессия → защищённая админка. Форма входа не спрашивает email: единственный получатель задан серверным ALLOWED_EMAIL, адрес из браузера не принимается и на странице входа не показывается. Отправитель — `Folio <onboarding@resend.dev>`; в этом режиме Resend разрешает доставку только владельцу своего аккаунта. Без собственного домена это ограничение подходит только личной панели.

Публичны только GET/HEAD `/login`, `/assets/login.css`, `/assets/login.js` и POST `/auth/request`, `/auth/verify`, `/auth/logout`. Все остальные страницы, ресурсы, API и неизвестные пути проверяют серверную сессию до маршрутизации. Анонимные `/`, `/sites`, `/settings` перенаправляются на вход; ресурсы/API возвращают 401. Заголовки Access и email не дают доступа. Нет конфигурации/хранилища → 503; неверный origin → 403. Все ответы no-store; CSP разрешает внешние скрипт/iframe Turnstile только на странице входа.

## Атомарность и ограничения

Один Durable Object `owner-auth-v1`, SQLite backend (`new_sqlite_classes`), одна строка состояния. Это минимальное хранилище авторизации, а не БД контента CMS. Workers KV не применяется из-за eventual consistency. SQLite Durable Objects доступны на Workers Free: [тариф и квоты](https://developers.cloudflare.com/durable-objects/platform/pricing/). На Free превышение квот приводит к отказам, а не автоматическому переходу на платный план.

`storage.transactionSync` атомарно читает, проверяет и записывает состояние. Внешние запросы выполняются вне транзакций. До отправки письма сохраняются квота и неподтверждённый код; только успешный ответ Resend активирует код. Неуспешная/неопределённая отправка расходует лимит и не разрешает вход. Поздний ответ старой отправки не активирует заменённый код. Состояние и квоты переживают перезапуск объекта.

- Случайный код: 6 цифр, Web Crypto без modulo bias; срок 10 минут от резервирования. Новая отправка заменяет предыдущий код.
- Код привязан к cookie браузера `__Host-folio-challenge` (256 бит). Без совпадения cookie чужой браузер не расходует попытки текущего кода.
- Максимум 5 попыток на код, дополнительно 30 попыток за скользящий час. Проверка, расход попытки, удаление кода и создание сессии — одна транзакция. Конкурентно код используется ровно один раз.
- Отправки: минимум 60 секунд между ними, максимум 5 за скользящий час и 20 за скользящие сутки. Эти лимиты общие для владельца, независимо от IP/браузера, и включают неудачные отправки.
- До Siteverify: максимум 30 непустых запросов в минуту с одного доверенного `CF-Connecting-IP`. IP хранится как SHA-256, счётчики живут минуту, максимум 256 активных IP. При заполнении новые IP временно получают 429. Нет доверия `X-Forwarded-For`.
- Siteverify проверяет success, точный hostname APP_ORIGIN и action `login`. Токены Turnstile одноразовые; отказ/таймаут не разрешает отправку. [Серверная проверка](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).
- POST требует точный Origin, JSON и тело до 4096 байт; cross-site/same-site Fetch Metadata отклоняются. Сервер принимает запросы только на APP_ORIGIN.

Сессия: случайный токен 256 бит, сервер хранит только SHA-256; cookie `__Host-folio-session`, Path=/, HttpOnly, Secure, SameSite=Strict, без Domain. Абсолютный срок — 1 час, без автоматического продления; максимум 10 активных сессий (самая старая вытесняется). Выход — POST с проверкой Origin, удаление серверной сессии и обеих cookies. Изменение AUTH_SECRET, разрешённого email или APP_ORIGIN отзывает прежние коды/сессии. Коды хранятся как HMAC-SHA256 с серверным секретом; plaintext существует только в памяти на время отправки.

Лимиты защищают почтовую квоту и перебор, но не гарантируют доступность против распределённого DDoS и исчерпания бесплатных квот. Любой анонимный посетитель, прошедший Turnstile, расходует общую квоту отправок — письмо всегда уходит на ALLOWED_EMAIL. Это следствие входа без ввода email и ограничение личного входа, без обещаний неуязвимости.

## Файлы и проверки

`src/auth.js` — конфигурация, криптография, cookies, обращение к фиксированному объекту; `src/auth-store.js` — код, лимиты, Resend, Turnstile и сессии; `src/worker.js` — маршруты/защита; `src/login.js` — вход; `src/ui.js` — прежняя админка и выход.

Секреты AUTH_SECRET, RESEND_API_KEY, TURNSTILE_SECRET_KEY и приватный ALLOWED_EMAIL — Worker secrets. APP_ORIGIN и публичный TURNSTILE_SITE_KEY тоже задаются через secrets ради единого способа настройки; только sitekey включается в страницу входа. Не хранить значения в Git/логах. Observability выключена, код не логирует тела, email, токены и ответы upstream.

`tests/worker.test.js` использует настоящую SQLite и криптографию с управляемыми часами и внешней сетью. `tests/runtime.test.js` запускает production-модули в workerd с SQLite Durable Object. `tests/preview-server.js` — только HTTPS localhost с временным состоянием и подменой доставки/CAPTCHA; `/__test/code` существует исключительно в тестовом entrypoint, отсутствует в production. Подмена внешнего виджета в браузерном сценарии не доказывает реальный Turnstile.

## Stage 02: создание сайтов — план от 2026-10-12, уточнён после ревью

Код Stage 02 не написан, секреты GitHub не заданы, внешние ресурсы не создавались. Ниже отделено то, что подтверждено документацией, от того, что требует проверки на живом аккаунте.

### Авторизация GitHub: GitHub App

GitHub App выбран вместо личного токена: installation-токен выпускается сервером автоматически на час, поэтому ручная ротация не нужна; права выдаются конечным списком и отзываются одним действием; приватный ключ живёт только в Worker secrets и не попадает в браузер, Git и логи.

| Вызов | Токен | Требуемое право |
|---|---|---|
| `GET /app/installations` | JWT приложения | — |
| `POST /app/installations/{id}/access_tokens` | JWT приложения | — |
| `GET /installation/repositories` | installation | `Metadata` (read) |
| `GET /repos/{owner}/{repo}` | installation | `Metadata` (read) |
| `POST /user/repos` | installation | `Administration` (write) либо `Repository creation` (write) |
| `GET`/`PUT` `/repos/{owner}/{repo}/contents/{path}` | installation | `Contents` (write) |
| `PUT /repos/{owner}/{repo}/topics` | installation | `Administration` (write) |
| `GET`/`POST` `/repos/{owner}/{repo}/pages` | installation | `Pages` (write) + `Administration` (write) |
| `GET /repos/{owner}/{repo}/pages/builds/latest` | installation | `Pages` (read) |
| `POST /repos/{owner}/{repo}/pages/builds` | installation | `Pages` (write) |

Итоговый набор прав приложения: `Administration` (write), `Pages` (write), `Contents` (write), `Metadata` (read). Право `Workflows` не запрашивается: каталог `.github/workflows` Folio не трогает, а без этого права GitHub отклоняет запись в него (документация Contents API). Основание по токенам и правам: [Create a repository for the authenticated user](https://docs.github.com/en/rest/repos/repos#create-a-repository-for-the-authenticated-user), [Create a GitHub Pages site](https://docs.github.com/en/rest/pages/pages#create-a-github-pages-site), [права приложений](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps).

JWT и токен: подпись `RS256`, claim'ы `iss` = App ID, `iat` на 60 секунд назад, `exp` не более 10 минут; далее `POST /app/installations/{id}/access_tokens` → installation-токен на 1 час, лимит 5 000 запросов в час. [JWT](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app), [лимиты](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).

Ключ приложения GitHub отдаёт в PEM `PKCS#1 RSAPrivateKey`, а WebCrypto принимает только `PKCS#8`: конвертация `openssl pkcs8 -topk8 -inform PEM -outform PEM -nocrypt -in key.pem -out key-pkcs8.key`. Подпись RS256 и импорт `pkcs8` в Workers поддержаны ([Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/)). `install_key_invalid` — отдельная понятная ошибка, если ключ загружен в неверном формате.

Секреты: `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY` (PKCS#8), `GITHUB_OWNER` — логин аккаунта, которому принадлежат сайты. `GITHUB_OWNER` нужен, чтобы выбрать установку, построить адрес `https://<owner>.github.io/<name>` и никогда не тронуть чужой аккаунт.

Выбор установки: `GET /app/installations` возвращает установки с объектом `account`; берётся та, у которой `account.login` совпадает с `GITHUB_OWNER`. Ни одной → `installation_missing` (503 с инструкцией установить приложение). Несколько подходящих → `installation_ambiguous` (ошибка конфигурации; Folio не угадывает). Ответы GitHub отображаются на ошибки: `401` → `github_auth_failed` (проверить App ID и ключ), `403`/`404` по конкретному репозиторию → `repository_access_denied`, `403` по лимиту → `rate_limited` со временем сброса.

Новые репозитории и область доступа: документацией не подтверждено, что созданный приложением репозиторий сразу попадает в установку с доступом «All repositories». Folio на это не полагается — сразу после создания репозиторий перечитывается тем же installation-токеном, и при `403`/`404` выводится «приложение не имеет доступа к новому репозиторию: переустановите его с доступом ко всем репозиториям», сайт остаётся незавершённым и доводится до конца повтором. Выдать себе доступ Folio не может: `PUT /user/installations/{id}/repositories/{repo_id}` требует пользовательского токена с правами администратора, а не installation-токена.

Пагинация: `GET /installation/repositories?per_page=100&page=N`; в ответе `total_count`, `repositories`, `repository_selection`. Страницы читаются до `total_count` с жёстким пределом (5 страниц); превышение — явная ошибка, а не молчаливое усечение списка. `repository_selection: selected` показывается предупреждением: при выборочном доступе новые сайты могут быть недоступны приложению.

### Принадлежность репозитория Folio

Три независимых сигнала, все ставятся сервером:

| Сигнал | Как создаётся | Что доказывает |
|---|---|---|
| Описание `Folio site: <заголовок>` | поле `description` в том же `POST /user/repos` | репозиторий создан Folio |
| Тема `folio-site` | `GET /repos/{owner}/{repo}/topics` → объединение с `folio-site` → `PUT` (endpoint заменяет набор целиком, чужие темы сохраняются; имена приводятся к нижнему регистру) | репозиторий ведёт Folio |
| `folio.json` в корне: `{"managedBy":"folio-cms","site":"<случайный id>","version":1,"title":"…"}` | `PUT /repos/{owner}/{repo}/contents/folio.json` | сайт создан полностью; файл — источник метаданных |

Правила принадлежности:

- **Свой** (можно доводить до конца): владелец репозитория равен `GITHUB_OWNER` и есть любой из трёх сигналов.
- **Завершён**: есть валидный `folio.json`. Только в этом состоянии допустима операция, изменяющая существующий файл; в Stage 02 таких операций нет.
- **Чужой**: сигналов нет — Folio не пишет ничего и отвечает `name_taken`. Отдельный чёрный список имён: `<owner>.github.io` (пользовательский сайт) и репозиторий движка `folio-cms` — не трогаются никогда, даже если у них появится тема.
- Первым сигналом выбрано описание, потому что оно записывается тем же запросом, что создаёт репозиторий: если процесс прервётся сразу после `POST /user/repos`, репозиторий уже помечен. Это же закрывает гонку двух одинаковых запросов: проигравший получает `422`, перечитывает репозиторий и видит пометку, а не «чужой» репозиторий.
- Повреждённый или удалённый `folio.json` при живых описании и теме: сайт показывается как «требует внимания»; восстановление — только по явному подтверждению в интерфейсе и только перезаписью `folio.json` (остальные файлы не меняются). Если исчезли все три сигнала, репозиторий снова считается чужим.
- Ложных попаданий в список практически нет: список строится по теме `folio-site`, а поставить её может только сам Folio или владелец вручную; полнота дополнительно подтверждается валидным `folio.json`.

### Создание сайта: сходимость вместо «идемпотентности из коробки»

Каждый шаг — «прочитать, затем дописать», для имени `name`:

1. `GET /repos/{owner}/{name}`: нет репозитория → создавать; есть и он «свой» → досоздавать; есть и он «чужой» → `name_taken`, ничего не менять.
2. `POST /user/repos {name, private:false, auto_init:true, description, homepage}`. `201` → дальше; `422` → перечитать и применить правило принадлежности (гонка); таймаут/`5xx` → перечитать: репозиторий есть и он свой → дальше, иначе явная ошибка шага.
3. Файлы `folio.json`, `index.html`, `.nojekyll`: только отсутствующие. `GET /contents/{path}` → `404` → `PUT`; существующий файл не перезаписывается никогда; `409`/`422` про `sha` → перечитать и сравнить содержимое: совпало → шаг выполнен, отличается → отказ с требованием подтверждения.
4. Тема: `GET /topics` → объединение → `PUT`.
5. Pages: `GET /pages`; `404` → `POST` `{build_type:"legacy", source:{branch:"main", path:"/"}}`; `200` → уже настроено, настройки владельца не меняются (в том числе не переводим `workflow` на `legacy`).
6. Ответ содержит фактическое состояние: репозиторий, файлы, тема, Pages (`status`, `html_url`). Сборка не ожидается.

Гарантируется: второй репозиторий для одного имени не создаётся; существующие файлы не перезаписываются; чужой репозиторий не изменяется; любой повтор приводит систему к одному и тому же состоянию; одновременные запросы на одно имя безопасны (единственная неидемпотентная операция — создание репозитория, и её гонка закрыта пометкой в описании).

Намеренно не обещается: ровно однократное выполнение шагов (лишние коммиты не создаются, потому что существующие файлы не переписываются, но повторный `PUT` отсутствующего файла возможен); откат уже созданного репозитория; удаление «осиротевшего» репозитория из интерфейса — при сбое он остаётся и доводится до конца повтором, а удалить его можно вручную в GitHub (отдельная операция удаления в Stage 02 не планируется). Это осознанный минимум: без второго хранилища, без очередей и без блокировок.

Сценарии, которые закрывают тесты: репозиторий создан, `folio.json` ещё не записан (досоздание по описанию); файлы записаны, тема или Pages — нет; GitHub выполнил операцию, а Worker получил таймаут (перечитать и продолжить); два одновременных запроса на одно имя; браузер закрыт в середине, запрос повторён позже (сайт виден как «не завершён» с кнопкой «Завершить»); имя занято чужим репозиторием; повреждённый `folio.json`.

### Публикация Pages

Настройка: `build_type: "legacy"` и `source: {branch:"main", path:"/"}` — сборка из ветки, без workflow-файлов и без права `Workflows`. `.nojekyll` записывается до включения Pages; GitHub описывает этот файл как признак того, что ветка не требует шага сборки, а не как гарантию поведения — поэтому в эксперименте (шаг 1) сборка проверяется и с файлом, и без него.

«Pages настроены» и «сайт доступен» — разные состояния. Первое: `GET /repos/{owner}/{repo}/pages` вернул сайт со `status`. Второе: реальный `GET https://<owner>.github.io/<name>/` из Worker со статусом `200` и меткой страницы `<meta name="folio-site" content="<name>">`. В интерфейсе это «публикуется» и «опубликован».

`status: building` — нормальное состояние: проверка повторяется отдельными запросами (`GET /api/sites/<name>/status`), без ожидания внутри запроса создания. `errored` — показывается `error` из `GET /pages/builds/latest` и предлагается повтор сборки (`POST /pages/builds`; на репозиторий допускается одна сборка одновременно). Недоступность GitHub в момент проверки — не «сайт сломан», а «статус неизвестен, проверьте снова».

Ограничение времени в Worker: на Free это 10 мс CPU на запрос, при этом ожидание сети в CPU не считается — ограничивают число подзапросов (50 на запрос на Free) и терпение клиента. Поэтому каждый вызов GitHub идёт с `AbortSignal.timeout(8000)` (как в Stage 01), запрос создания делает не более ~12 подзапросов и никогда не ждёт сборку, а статус публикации проверяется отдельными вызовами. Исчерпание бюджета — ошибка «не завершено, повторите»; повтор безопасен. [Лимиты Workers](https://developers.cloudflare.com/workers/platform/limits/).

### Адреса статей: требование сохраняется, нужен эксперимент

Требование владельца остаётся в силе: `/site-name/YYMMDD` без `.html` и без завершающего слеша. Окончательный вывод не сделан.

Наблюдения на чужих Pages-сайтах 2026-10-12 (curl, `Server: GitHub.com`): каталог с `index.html` без слеша → `301` на адрес со слешем; файл без расширения (`CNAME`, `.nojekyll`) → `200` с `Content-Type: application/octet-stream`; несуществующий путь → `404` с содержимым `404.html`. Это наблюдения, а не доказательство: MIME-таблица и поведение Pages могут зависеть от содержимого файла, заголовков запроса и от того, обрабатывает ли ветку Jekyll.

План эксперимента на своём пробном репозитории (запуск только после разрешения владельца):

| Проверка | Адрес | Что фиксируем |
|---|---|---|
| базовая страница | `/probe/` | `200`, `Content-Type` |
| каталог без слеша | `/probe/a` | статус, `Location`, итоговый адрес в адресной строке |
| каталог со слешем | `/probe/a/` | `200`, MIME |
| `.html` без расширения в адресе | `/probe/b` при файле `b.html` | есть ли подстановка расширения |
| файл без расширения с HTML | `/probe/c` | статус, MIME, отображается или скачивается |
| то же с `Accept: text/html` | `/probe/c` | влияет ли согласование содержимого |
| Jekyll-пост | `/probe/YYMMDD`, `/probe/YYMMDD/` | раскладка файлов, статус, `Location`, MIME |
| ветка без `.nojekyll` | `/probe/` | влияет ли Jekyll на раскладку |
| поддержка `_redirects` | `/probe/d` при `d/index.html` и `_redirects` | влияет ли файл вообще |
| поведение 404 | `/probe/nope` | статус и содержимое (только измерение) |

Успехом считается только комбинация «`200` + `text/html` + адрес ровно `/YYMMDD`» без редиректа. Если её не даёт ни одна проверка, решение принимает владелец: принять `301` (адрес, который набирают и пересылают, не меняется, но финальный адрес получает слеш) либо изменить требование. Вариант с `404.html` как механизмом публикации статей не применяется без отдельного решения владельца.

### Список сайтов, независимость, телефон

Список сайтов — `GET /installation/repositories` с фильтром по теме `folio-site`; состояние публикации и доступность проверяются отдельно. Своего хранилища нет: метаданные — в репозитории, `folio.json` позже становится источником заголовка и настроек. Единственный Durable Object `owner-auth-v1` остаётся хранилищем авторизации; новых binding и постоянного кэша не добавляется (installation-токен кэшируется в памяти изолята не дольше часа; лишний выпуск токена безвреден).

Независимость: у каждого сайта свой репозиторий, история, Pages-сайт и адрес. Folio не пишет общие файлы, поэтому поломка или удаление одного сайта не затрагивает другие и сам `tmksdm/folio-cms`.

Телефон: форма имени и заголовка с крупными целями, нормализация имени (нижний регистр, пробелы в дефисы), инлайн-проверка, состояния «создаётся», «публикуется», «опубликован» с кнопкой «проверить снова», повтор при сбое, ссылка на сайт.
