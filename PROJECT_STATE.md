## План Stage 02: что уточнено

Полный текст — в `ARCHITECTURE.md` («Stage 02: создание сайтов»), шаги и критерии приёмки — в `ROADMAP.md`.

- **Авторизация.** GitHub App, installation-токен выпускается по JWT (RS256) на час, лимит 5 000 запросов в час. Права приложения: `Administration` (write), `Pages` (write), `Contents` (write), `Metadata` (read); `Workflows` не запрашивается. По каждому вызову права выписаны таблицей с источником. Ключ GitHub отдаёт в `PKCS#1`, WebCrypto принимает `PKCS#8` — конвертация через `openssl pkcs8 -topk8 -nocrypt`.
- **Установка.** Выбирается по `GITHUB_OWNER` (новый секрет, вместе с `GITHUB_APP_ID` и `GITHUB_APP_PRIVATE_KEY`); нет установки — `installation_missing`, несколько — `installation_ambiguous`; `401`/`403`/`404`/`429` отображаются на понятные коды. Список репозиториев читается с пагинацией (`total_count`, `repository_selection`) и жёстким пределом страниц. Попадание только что созданного репозитория в область доступа приложения документацией не подтверждено, поэтому проверяется чтением сразу после создания, а не предполагается.
- **Принадлежность.** Три сигнала: описание `Folio site: …` (записывается тем же запросом, что создаёт репозиторий — это закрывает гонку), тема `folio-site` (ставится `PUT` с предварительным чтением, чтобы не потерять чужие темы) и `folio.json` с `managedBy` (признак завершённости и источник метаданных). «Чужой» репозиторий не изменяется; `folio-cms` и `<owner>.github.io` не трогаются никогда. Повреждённый `folio.json` восстанавливается только по явному подтверждению.
- **Сходимость.** Каждый шаг — «прочитать, затем дописать»; существующие файлы не перезаписываются; повтор после сбоя на любом шаге доводит сайт до конца; два одновременных запроса на одно имя безопасны. Явно **не** обещается: ровно однократное выполнение шагов, откат созданного репозитория, операция удаления сайта в интерфейсе. Никаких очередей, блокировок и второго хранилища.
- **Pages.** Сборка из ветки `main` (`build_type: legacy`, `path: /`), `.nojekyll` пишется до включения Pages. «Pages настроены» (`GET /pages`) и «сайт доступен» (реальный `GET https://<owner>.github.io/<name>/` со статусом `200` и меткой страницы) — разные состояния в интерфейсе. Сборка не ожидается внутри запроса: статус проверяется отдельными вызовами; `errored` показывает причину и предлагает повтор сборки. Ограничители в Worker: 10 мс CPU на Free (ожидание сети в CPU не считается) и 50 подзапросов на запрос — поэтому у каждого вызова GitHub `AbortSignal.timeout(8000)`, не более ~12 подзапросов на создание и никакого ожидания сборки.
- **Адреса статей.** Требование владельца сохранено без изменений. Окончательный вывод не сделан: составлена таблица измерений на пробном репозитории (статусы, `Location`, `Content-Type`, итоговый адрес в браузере, Jekyll с `.nojekyll` и без, `_redirects`, в том числе файл без расширения и `Accept: text/html`). Успех — только `200` + `text/html` по адресу ровно `/YYMMDD`; иначе решение принимает владелец. Вариант с `404.html` как механизмом публикации не применяется без отдельного решения.

## Наблюдения на чужих GitHub Pages 2026-10-12

Запросы curl к реальным Pages-сайтам (ответы `Server: GitHub.com`), не к своему аккаунту:

| Что проверено | Где | Результат |
|---|---|---|
| каталог с `index.html`, запрос без слеша | `jekyllrb.com/docs`, `github.github.com/gfm` | `301` → адрес со слешем, затем `200` |
| файл без расширения | `jekyllrb.com/CNAME`, `jekyllrb.com/.nojekyll` | `200`, `Content-Type: application/octet-stream` |
| несуществующий путь | `jekyllrb.com/zzz-…`, `github.github.com/gfm/zzz-nope` | `404` с содержимым `404.html` сайта |

Это наблюдения на чужих сайтах, а не доказательство для нашей схемы: поведение может зависеть от содержимого файла, заголовков запроса и обработки Jekyll. Пробный репозиторий не создавался — это шаг 1 плана, требующий отдельного разрешения.
