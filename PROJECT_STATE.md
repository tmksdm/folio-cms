## План Stage 02 (подготовлен, ожидает ревью)

Цель: из админки, в том числе с телефона, создавать независимые сайты и получать их адреса `https://tmksdm.github.io/<name>`; каждый сайт — отдельный GitHub-репозиторий; без ручных действий владельца в GitHub.

- Авторизация GitHub: **GitHub App** с installation-токенами. Документация GitHub подтверждает, что `POST /user/repos` принимает installation access tokens при праве `Administration: write` (или `Repository creation: write`), а `POST /repos/{owner}/{repo}/pages` требует `Pages: write` + `Administration: write`. Токен выпускается сервером по JWT (RS256) на час и обновляется автоматически, ручная ротация не нужна; лимит — 5 000 запросов в час.
- Особенность настройки: GitHub отдаёт ключ приложения в PEM `PKCS#1`, а WebCrypto принимает только `PKCS#8` — нужна конвертация `openssl pkcs8 -topk8 -nocrypt`. Подпись RS256 и импорт `pkcs8` в Workers поддержаны.
- Состояния и базы данных нет: шаги создания идемпотентны, список сайтов и статус публикации читаются из GitHub (`GET /installation/repositories` с фильтром по теме `folio-site`); единственный Durable Object остаётся хранилищем авторизации.
- Новые секреты (пока не создавались): `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`.
- Полное обоснование, шаги и риски — в `ARCHITECTURE.md` («Stage 02: создание сайтов») и `ROADMAP.md` (шаги 1–5, критерии приёмки).

## Измерения GitHub Pages 2026-10-12

Проверено запросами curl к реальным Pages-сайтам (ответы с `Server: GitHub.com`):

| Что проверено | Где | Результат |
|---|---|---|
| каталог с `index.html`, запрос без слеша | `jekyllrb.com/docs`, `github.github.com/gfm` | `301` → адрес со слешем, затем `200` |
| файл без расширения | `jekyllrb.com/CNAME`, `jekyllrb.com/.nojekyll` | `200`, `Content-Type: application/octet-stream` |
| несуществующий путь | `jekyllrb.com/zzz-…`, `github.github.com/gfm/zzz-nope` | `404` с содержимым `404.html` сайта |

Следствие: адрес статьи одновременно без `.html` и без завершающего слеша статический Pages отдать не может. Варианты (A — каталог `YYMMDD/index.html` с `301`; B — `404.html` с клиентским разбором пути и статусом `404`; C — `YYMMDD.html`) описаны в `ARCHITECTURE.md`; решение принимает владелец. Пробный репозиторий для подтверждения на своём аккаунте и проверки `_redirects` не создавался — это шаг 1 плана, он требует отдельного разрешения.
