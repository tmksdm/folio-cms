# Folio CMS

Собственная универсальная CMS для нескольких независимых сайтов. Единая русскоязычная админка на Cloudflare Workers; с телефона можно будет создавать сайты, писать Markdown-статьи, загружать изображения, сохранять черновики и публиковать материалы.

- `folio-cms` содержит только движок и админку. Каждый сайт — отдельный GitHub-репозиторий с публичной ссылкой `https://tmksdm.github.io/site-name`; для главной допускается перенаправление Pages на адрес со слешем.
- Адреса статей: `<base>/YYMMDD`, `<base>/YYMMDD-2`, `<base>/YYMMDD-3`, без `.html` и завершающего слеша. Совместимость требуется доказать на реальном GitHub Pages на этапе публикации.
- Вход в админку — собственный одноразовый email-код через Resend, Turnstile и защищённую cookie-сессию, только один серверно настроенный адрес. Cloudflare Access/Zero Trust не используются. GitHub не используется для входа.
- GitHub API вызывается только сервером; секреты не попадают в браузер или Git. Без традиционной БД контента, обязательных платных сервисов и готовой сторонней CMS.
- Повседневная работа владельца выполняется из админки, включая телефон, без ручных коммитов или настройки каждого сайта в GitHub. Публичный сайт получит минималистичный адаптивный дизайн, список статей, полнотекстовый поиск, пагинацию и светлую/тёмную темы; затем — backup и восстановление.

## Stage 01 — принят

Минимальная адаптивная админка: обзор, пустой список сайтов, сведения о подтверждённой сессии, выход с отзывом серверной сессии. Все маршруты админки защищены серверной сессией; публичны только вход и необходимые ресурсы/API авторизации. SQLite Durable Object для атомарных кодов/лимитов. Подготовка Worker, автоматические проверки и инструкция развёртывания без Zero Trust.

Владелец принял Stage 01: админка опубликована на Cloudflare Workers Free (`https://folio-admin.doridupa.workers.dev`), подтверждены 28 автоматических тестов, production-сборка, доставка кодов через Resend, Turnstile, вход без поля email, защищённые сессии и выход. Последний принятый коммит — `7b26ddd`.

## Stage 02 — план: создание сайтов

Цель: из единой админки (в том числе с телефона) создать новый независимый сайт и получить его публичный адрес `https://tmksdm.github.io/site-name`. Каждый сайт — отдельный GitHub-репозиторий; владелец не выполняет ручных действий в GitHub.

Кратко: серверная авторизация GitHub через GitHub App с автоматическими installation-токенами и минимальными правами; у каждого репозитория явные маркеры принадлежности Folio, поэтому чужой репозиторий не изменяется; шаги создания сходятся к одному состоянию при повторе, без второго хранилища и без очередей; список сайтов выводится из GitHub; секреты только в Worker secrets.

План (шаги, файлы, проверки, риски и критерии приёмки) — в `ROADMAP.md`, техническое обоснование — в `ARCHITECTURE.md`.

**Не реализовано.** Кода Stage 02, секретов GitHub и внешних ресурсов нет; реализация начинается только после явного разрешения владельца.

## Адреса статей: требование сохраняется

Требование из начала документа остаётся в силе: `<base>/YYMMDD` без `.html` и без завершающего слеша. Измерения на чужих Pages-сайтах показали, что каталог с `index.html` отвечает `301` на адрес со слешем, а файл без расширения отдаётся как `application/octet-stream`, — но это чужие сайты и не доказательство для нашей схемы. Совместимость проверяется минимальным экспериментом на своём пробном репозитории (шаг 1 плана, таблица измерений в `ARCHITECTURE.md`), а не предположениями.

Если эксперимент не даст адреса без расширения и без слеша одновременно, решение принимает владелец: принять `301` (адрес для набора и пересылки не меняется) или изменить требование. Вариант с `404.html` как механизмом публикации статей не применяется без отдельного решения владельца. До этого момента публикация статей (Stage 03) не планируется.

## Границы

GitHub-интеграция ограничена созданием сайтов и настройкой публикации; редактора статей, загрузки файлов и публичного дизайна пока нет. Старые требования Stage 00 отменены новым заданием; документы старой ветки не задают текущую дорожную карту.

Приёмка каждого этапа: сборка для Worker, автоматические проверки и ручная проверка владельцем. Локальные тесты не доказывают опубликованную защиту. После этапа — внешнее ревью; следующий этап только по явному одобрению.
