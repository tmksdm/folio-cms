# Этапы

Каждый этап заканчивается проверками, коммитом в GitHub и остановкой для внешнего ревью. По указанию пользователя от 2026-10-11 результат публикуется прямо в `main`. Следующий этап требует явного одобрения. Старая дорожная карта Stage 00 отменена.

| Этап | Один результат | Статус |
|---|---|---|
| 01 — Первая работающая админка | Собственный адаптивный интерфейс; Cloudflare Workers; собственный email-код через Resend; Turnstile; SQLite Durable Object; защищённая сессия | Принят владельцем, коммит `7b26ddd` |
| 02 — Создание сайтов | Создание независимых сайтов из админки; автоматическое создание GitHub-репозиториев и настройка Pages; несколько сайтов; ссылки `https://tmksdm.github.io/site-name` | План уточнён после второго ревью 2026-10-13, ожидает ревью |
| 03 — Редактор и публикация | Создание, редактирование, удаление Markdown-статей; изображения; черновики и публикация; автоматические постоянные `/YYMMDD`, `/YYMMDD-2` и далее; GitHub API без ручных коммитов | Не разрешён |
| 04 — Публичный сайт | Минималистичный адаптивный дизайн; название и список статей; полнотекстовый поиск; пагинация; светлая/тёмная темы; корректные статьи и изображения | Не разрешён |
| 05 — Доводка | Резервное копирование и восстановление; безопасность; телефон и компьютер; исправления и финальная документация | Не разрешён |

Этапы 03–05 не разрешены к реализации.

## Обязательные границы

- `tmksdm/folio-cms` — только движок и админка. Все публичные сайты — в отдельных репозиториях на GitHub Pages, несколько независимых сайтов из одной панели.
- Полноценное повседневное использование с телефона, без ручной работы владельца с GitHub.
- Ссылки на главную — без завершающего слеша; допускается перенаправление GitHub Pages на корень со слешем.
- Статьи — без `.html` и завершающего слеша; требование сохраняется, совместимость проверяется экспериментом (шаг 1). Если Pages не поддерживает требование, остановиться и согласовать решение с владельцем.
- Без традиционной БД контента, обязательных платных сервисов, секретов в браузере и публичных репозиториях. Будущие требования учитывать без преждевременной реализации.

## Stage 02 — план реализации

Обоснование вариантов авторизации, правила принадлежности репозитория и разбор сбоев — в `ARCHITECTURE.md`, раздел «Stage 02: создание сайтов».

### Шаг 1. Предварительная проверка авторизации и адреса статей

- Что, часть A (авторизация): приложение GitHub устанавливается на аккаунт владельца с доступом ко всем репозиториям, Folio создаёт **один** пробный публичный репозиторий своим installation-токеном, записывает в него `folio.json`, включает Pages и читает статус. Один прогон подтверждает или опровергает всю схему на личном аккаунте.
- Что, часть B (адреса статей): в том же пробном репозитории разложены `index.html`, каталог `a/index.html`, файл `b.html`, файл без расширения `c`, `.nojekyll`, `404.html` и `_redirects`; измерения curl и в браузере по таблице из `ARCHITECTURE.md`, включая Jekyll-пост `/YYMMDD` и ветку без `.nojekyll`.
- Файлы: внешний пробный репозиторий; результаты — в `PROJECT_STATE.md`, вывод — в `ARCHITECTURE.md`.
- Проверка: подтверждение, что installation-токен создаёт репозиторий в личном аккаунте, пишет файлы и включает Pages; таблица фактических статусов, `Location`, `Content-Type` и итогового адреса в адресной строке.
- Риск: если создание репозитория installation-токеном на личном аккаунте не сработает, включается запасной вариант A (install); если требование к адресам невыполнимо в точном виде, решение принимает владелец — принять `301` или изменить требование. Вариант с `404.html` как механизмом публикации статей не применяется без отдельного решения.
- Согласование: создание приложения и репозитория — только с явного разрешения владельца. Ничего из этого ещё не выполнялось.

### Шаг 2. Серверный клиент GitHub API

- Что: конфигурация интеграции; JWT (RS256, PKCS#8) и выпуск installation-токена; выбор установки по `GITHUB_OWNER`; чтение списка репозиториев с пагинацией и `repository_selection`; отображение ошибок (`401`, `403`, `404`, `409`, `422`, `429`, `5xx`, таймаут) на понятные коды; запрет логирования секретов и тел.
- Файлы: новый `src/github.js`; конфигурация рядом с `authConfig`; `.dev.vars.example`; `tests/github.test.js`.
- Проверка: тесты на настоящей криптографии (локально сгенерированная пара ключей) с подменённой сетью: claim'ы JWT, выпуск и переиспользование токена, истечение, отсутствие и несколько установок, `401`/`403`/`429`, пагинация и её предел. Закрытый маршрут `/api/github/status` под сессией показывает приложение, аккаунт установки, права, `repository_selection` и остаток лимита.
- Риск: реальные права установки проверяются только на живом GitHub (шаг 1, часть A).

### Шаг 3. Принадлежность и сходимость создания сайта

- Что: доказательство принадлежности только по `folio.json`; подсказки (описание, тема) прав не дают; явное подтверждение владельца для репозитория без `folio.json`, после которого записывается ровно один файл; досоздание проверенного сайта; отказ на чужой репозиторий; запрет перезаписи существующих файлов; объединение тем; включение Pages без изменения чужих настроек.
- Файлы: новый `src/sites.js`, маршруты в `src/worker.js`, расширение `tests/worker.test.js`.
- Проверка: тесты со стендом GitHub — создание с нуля; повторный запрос после сбоя на каждом шаге (после создания репозитория, после файлов, после темы); потерянный ответ и таймаут; два одновременных запроса на одно имя; занятое имя чужого репозитория (`folio-cms`, `<owner>.github.io`); повреждённый `folio.json`; репозиторий с описанием и темой, но без `folio.json` (запись запрещена до подтверждения); проверка, что подтверждение не открывает доступ к репозиториям из чёрного списка.
- Риск: сценарии «репозиторий недоступен приложению» и «Pages не включаются с первого раза» воспроизводятся только на живом GitHub.

### Шаг 4. Список сайтов, статус публикации и интерфейс

- Что: `GET /api/sites` — репозитории установки с темой `folio-site`, из которых показываются только проверенные по `folio.json`; `GET /api/sites/<name>/status` — проверка публикации (`building`/`built`/`errored` плюс реальный `200` и метка страницы); панель «Сайты» с формой создания, состояниями, подтверждением, повтором и ссылкой на сайт.
- Файлы: `src/worker.js`, `src/ui.js`, `tests/preview-server.js`, `tests/fixtures.js`, `tests/browser-check.js`.
- Проверка: браузерный сценарий на HTTPS-стенде с подменённым GitHub — создание, «публикуется», «опубликован», занятое имя, ошибка сети и повтор, «требует подтверждения» с кнопкой подтверждения, проверка статуса по кнопке; ширины 1440/390/320 без горизонтальной прокрутки, клавиатура.
- Риск: подмена GitHub в стенде не доказывает реальную публикацию — это отдельная ручная проверка владельца.

### Шаг 5. Развёртывание и ручная приёмка владельцем

- Что: раздел в `DEPLOY.md` — создание GitHub App, доступ ко всем репозиториям, конвертация ключа, три новых секрета; владелец публикует и создаёт первый сайт с телефона.
- Файлы: `DEPLOY.md`, `PROJECT_STATE.md`.
- Проверка: сайт открывается по `https://tmksdm.github.io/<name>`; повторные нажатия не создают второй репозиторий; отличия `repository_selection` и поведение при отзыве прав проверены на живом аккаунте.
- Риск: одноразовая настройка выполняется руками; неверный формат ключа и выборочный доступ к репозиториям ловятся понятными ошибками, но требуют внимания владельца.

## Критерии приёмки Stage 02

1. Совместимость авторизации подтверждена живой проверкой: installation-токен создаёт репозиторий в личном аккаунте, пишет файлы и включает Pages; если нет — работает запасной вариант A, и это отражено в документации.
2. С телефона из админки создаётся сайт по имени и заголовку; адрес `https://tmksdm.github.io/<name>` открывается и отдаёт страницу созданного сайта. Публикация асинхронная: интерфейс показывает «публикуется» и даёт проверить статус повторно, гарантия «за 1–2 минуты» не требуется.
3. Владелец не выполняет ручных действий в GitHub при создании сайта (кроме одноразовой настройки приложения); секреты не попадают в браузер, Git и логи.
4. Повторные нажатия, перезагрузка и повтор после сбоя не создают второй репозиторий и не переписывают существующие файлы; незавершённое создание доводится до конца из админки.
5. Репозиторий без проверенного `folio.json` не изменяется автоматически: он либо получает явное подтверждение владельца, либо остаётся нетронутым; `folio-cms` и `<owner>.github.io` не изменяются никогда.
6. Минимум два сайта работают независимо: у каждого свой репозиторий, адрес и история; сбой одного не влияет на другой.
7. Все новые маршруты требуют серверную сессию; анонимные получают `401` или `303` на вход, как сейчас.
8. Сбои и лимиты GitHub (таймаут, `401`, `403`, `429`, `5xx`) дают понятную ошибку и никогда — молчаливый успех; различаются «не создан», «создан, публикуется», «опубликован» и «статус неизвестен».
9. Традиционной базы данных нет: список сайтов и состояние выводятся из GitHub; единственный Durable Object остаётся хранилищем авторизации.
10. `npm run check`, `npm test`, `npm run build` проходят; браузерный сценарий на локальном стенде проходит.
11. Вопрос адресов статей закрыт экспериментом на своём Pages и явным решением владельца — до начала Stage 03.
