# Этапы

Каждый этап заканчивается проверками, коммитом в GitHub и остановкой для внешнего ревью. По указанию пользователя от 2026-10-11 результат публикуется прямо в `main`. Следующий этап требует явного одобрения. Старая дорожная карта Stage 00 отменена.

| Этап | Один результат | Статус |
|---|---|---|
| 01 — Первая работающая админка | Собственный адаптивный интерфейс; Cloudflare Workers; собственный email-код через Resend; Turnstile; SQLite Durable Object; защищённая сессия | Принят владельцем, коммит `7b26ddd` |
| 02 — Создание сайтов | Создание независимых сайтов из админки; автоматическое создание GitHub-репозиториев и настройка Pages; несколько сайтов; ссылки `https://tmksdm.github.io/site-name` | План подготовлен 2026-10-12, ожидает ревью |
| 03 — Редактор и публикация | Создание, редактирование, удаление Markdown-статей; изображения; черновики и публикация; автоматические постоянные `/YYMMDD`, `/YYMMDD-2` и далее; GitHub API без ручных коммитов | Не разрешён |
| 04 — Публичный сайт | Минималистичный адаптивный дизайн; название и список статей; полнотекстовый поиск; пагинация; светлая/тёмная темы; корректные статьи и изображения | Не разрешён |
| 05 — Доводка | Резервное копирование и восстановление; безопасность; телефон и компьютер; исправления и финальная документация | Не разрешён |

Этапы 03–05 не разрешены к реализации.

## Обязательные границы

- `tmksdm/folio-cms` — только движок и админка. Все публичные сайты — в отдельных репозиториях на GitHub Pages, несколько независимых сайтов из одной панели.
- Полноценное повседневное использование с телефона, без ручной работы владельца с GitHub.
- Ссылки на главную — без завершающего слеша; допускается перенаправление GitHub Pages на корень со слешем.
- Статьи — без `.html` и завершающего слеша; доказать реальными тестами до принятия публикации на Stage 03. Если Pages не поддерживает требование, остановиться и согласовать решение.
- Без традиционной БД контента, обязательных платных сервисов, секретов в браузере и публичных репозиториях. Будущие требования учитывать без преждевременной реализации.

## Stage 02 — план реализации

Техническое обоснование — в `ARCHITECTURE.md`, раздел «Stage 02: создание сайтов». Порядок шагов задан так, чтобы каждый шаг имел проверяемый результат и не требовал следующего.

### Шаг 1. Адреса статей на реальном GitHub Pages (решение владельца)

- Что: пробный репозиторий с `index.html`, каталогом `YYMMDD/index.html`, файлом без расширения, `.nojekyll`, `404.html` и файлом `_redirects`; измерение статусов, `Location` и `Content-Type` через curl.
- Файлы: внешний пробный репозиторий; результат измерения — в `PROJECT_STATE.md`, вывод — в `ARCHITECTURE.md`.
- Проверка: таблица фактических ответов на 6–8 адресов вместо предположений.
- Риск: подтвердит, что строгое требование «без `.html` и без слеша» на статическом Pages невыполнимо; тогда владелец выбирает вариант A, B или C, и только после этого планируется Stage 03.
- Замечание: измерение на чужих Pages-сайтах уже показало `301` для каталогов, `octet-stream` для файлов без расширения и `404` с содержимым `404.html`; шаг нужен, чтобы подтвердить это на своём репозитории и проверить `_redirects`.
- Согласование: создать репозиторий можно только с явного разрешения владельца.

### Шаг 2. Серверный клиент GitHub API

- Что: конфигурация интеграции, JWT (RS256, PKCS#8), выпуск и кэширование installation-токена, поиск установки, список репозиториев установки, нормализация ошибок (401/403/404/409/422/429, 5xx, таймаут) без логирования секретов и тел.
- Файлы: новый `src/github.js`; конфигурация рядом с `authConfig`; `.dev.vars.example`; тесты `tests/github.test.js`.
- Проверка: тесты на настоящей криптографии (локально сгенерированная пара ключей) с подменённой сетью: корректность claim'ов JWT, выпуск и переиспользование токена, истечение, отображение ошибок. Закрытый маршрут `/api/github/status` под сессией показывает логин приложения, аккаунт установки, права и остаток лимита.
- Риск: формат ключа и права установки проверяются только на реальном GitHub (шаг 5); до этого всё подтверждено тестами, а не API.

### Шаг 3. Создание сайта идемпотентными шагами

- Что: `POST /api/sites` с `{name, title}`: проверка и нормализация имени, создание репозитория, запись `folio.json`/`index.html`/`.nojekyll`, включение Pages, ожидание сборки; ответ содержит статус каждого шага.
- Файлы: новый `src/sites.js`, маршруты в `src/worker.js`, расширение `tests/worker.test.js`.
- Проверка: тесты со стендом GitHub — успешное создание, повторный запрос после частичной ошибки, занятое имя чужого репозитория (`folio-cms`), `409` «Pages уже включены», `403` лимита, таймаут; ни один шаг не создаёт второй репозиторий.
- Риск: включение Pages до появления файлов и права установки при выборочном доступе к репозиториям проверяются на живом GitHub.

### Шаг 4. Список сайтов и интерфейс админки

- Что: `GET /api/sites` возвращает сайты из `GET /installation/repositories` (фильтр по теме) со статусом публикации и адресом; панель «Сайты» получает форму создания, шаги публикации, повтор и ссылки.
- Файлы: `src/worker.js`, `src/ui.js` (панель и стили), `tests/preview-server.js`, `tests/fixtures.js`, `tests/browser-check.js`.
- Проверка: браузерный сценарий на HTTPS-стенде с подменённым GitHub — создание, состояние «публикуется», готовый сайт, занятое имя, ошибка сети и повтор; ширины 1440/390/320 без горизонтальной прокрутки, клавиатура.
- Риск: подмена GitHub в стенде не доказывает реальную публикацию — это отдельная ручная проверка владельца.

### Шаг 5. Развёртывание и ручная приёмка владельцем

- Что: раздел в `DEPLOY.md` о создании GitHub App, конвертации ключа и двух новых секретах; владелец публикует и создаёт первый сайт с телефона.
- Файлы: `DEPLOY.md`, `PROJECT_STATE.md`.
- Проверка: сайт открывается по адресу `https://tmksdm.github.io/<name>` и отвечает `200`; повторные нажатия не создают второй репозиторий.
- Риск: одноразовая настройка приложения выполняется вручную и требует внимательности при выдаче прав и выборе доступа к репозиториям.

## Критерии приёмки Stage 02

1. С телефона из админки создаётся сайт по имени и заголовку; в течение 1–2 минут он открывается по `https://tmksdm.github.io/<name>` со статусом `200` и ожидаемой страницей.
2. Владелец не выполняет ручных действий в GitHub при создании сайта (кроме одноразовой настройки приложения); секреты не попадают в браузер, Git и логи.
3. Повторные нажатия, перезагрузка и повтор после сбоя не создают второй репозиторий и не дублируют коммиты; незавершённое создание доводится до конца из админки.
4. Занятое имя без маркера Folio даёт понятное сообщение и не изменяет чужой репозиторий.
5. Минимум два сайта работают независимо: у каждого свой репозиторий, адрес и история; сбой одного не влияет на другой.
6. Все новые маршруты требуют серверную сессию; анонимные получают `401` или `303` на вход, как сейчас.
7. Сбои и лимиты GitHub (таймаут, `403`, `429`, `5xx`) дают понятную ошибку и никогда — молчаливый успех; интерфейс различает «не создан», «создан, публикуется» и «опубликован».
8. Традиционной базы данных нет: список сайтов и их состояние выводятся из GitHub; единственный Durable Object остаётся хранилищем авторизации.
9. `npm run check`, `npm test`, `npm run build` проходят; браузерный сценарий на локальном стенде проходит.
10. Вопрос адресов статей решён измерением и явным решением владельца до начала Stage 03.
