Каждый этап заканчивается проверками, коммитом в GitHub и остановкой для внешнего ревью. По указанию пользователя от 2026-10-11 результат публикуется прямо в `main`. Следующий этап требует явного одобрения. Старая дорожная карта Stage 00 отменена.

|---|---|---|
| 01 — Первая работающая админка | Собственный адаптивный интерфейс; Cloudflare Workers; собственный email-код через Resend; Turnstile; SQLite Durable Object; защищённая сессия | Принят владельцем, коммит `7b26ddd` |
| 02 — Создание сайтов | Создание независимых сайтов из админки; автоматическое создание GitHub-репозиториев и настройка Pages; несколько сайтов; ссылки `https://tmksdm.github.io/site-name` | Шаг 1.1 принят владельцем (ревью `674d540`); тестовый репозиторий удалён, план шагов 2–5 подготовлен; ожидает ревью |

| 05 — Доводка | Резервное копирование и восстановление; безопасность; телефон и компьютер; исправления и финальная документация | Не разрешён |

Этапы 03–05 не разрешены к реализации.

## Обязательные границы

- `tmksdm/folio-cms` — только движок и админка. Все публичные сайты — в отдельных репозиториях на GitHub Pages, несколько независимых сайтов из одной панели.
- Полноценное повседневное использование с телефона, без ручной работы владельца с GitHub.
- Ссылки на главную — без завершающего слеша; допускается перенаправление GitHub Pages на корень со слешем.
- Статьи — без `.html` и завершающего слеша; требование проверено живым экспериментом 2026-10-13 и **выполнимо**: статический файл `YYMMDD.html` отдаётся по адресу `/YYMMDD` со статусом `200 text/html` и без перенаправления (собственное измерение [И], независимым ревьюером не проверено; измерения — в `ARCHITECTURE.md` и `STAGE02_STEP1_EVIDENCE.md`).
- Без традиционной БД контента, обязательных платных сервисов, секретов в браузере и публичных репозиториях. Будущие требования учитывать без преждевременной реализации.

## Stage 02 — план реализации

Обоснование вариантов авторизации, правила принадлежности репозитория и разбор сбоев — в `ARCHITECTURE.md`, раздел «Stage 02: создание сайтов»; уровни доказательств ([П] живой GitHub, [И] собственное HTTP-измерение, [Д] документация) и рекомендация по варианту A — там же. Очищенные свидетельства измерений — в `STAGE02_STEP1_EVIDENCE.md`.

### Шаг 1. Предварительная проверка авторизации и адреса статей — выполнен 2026-10-13

Пробный репозиторий — [`tmksdm/folio-pages-probe`](https://github.com/tmksdm/folio-pages-probe), сайт — `https://tmksdm.github.io/folio-pages-probe/`. Полные измерения и таблицы — в `ARCHITECTURE.md`, раздел «Stage 02: создание сайтов».

- Часть A (авторизация) [П]. Приложение `folio-cms-pages` (App ID 5299581) установлено владельцем на `tmksdm` с доступом ко всем репозиториям; выданные права — `Administration`, `Contents`, `Pages` (write), `Metadata` (read). Installation-токен создаёт коммиты и файлы (`201`), включает Pages (`201`, `build_type: legacy`, `https_enforced: true`), читает статус сборки (`200`) и видит 41 репозиторий из 41, включая новый. **Создание репозитория installation-токеном не работает**: `POST /user/repos` → `403` с телом `Rate Limit Exceeded`, воспроизводимо (три попытки за три минуты) при неизрасходованном первичном лимите (5992 из 6000) и выданном праве `Administration` (write). **Причина `403` не установлена**: неизрасходованный первичный лимит не исключает secondary rate limiting, abuse detection и других ограничений GitHub. Репозиторий создал user OAuth-токен `gh` (`201`) — это другой тип токена, а не user access token приложения. Вариант D (installation-токен на всё) отклонён измерением, утверждён вариант A (шаг 1.1 подтвердил его).
- Часть B (адреса статей) [И]. Требование выполнено: при статическом файле `YYMMDD.html` адрес `/YYMMDD` отдаёт `200 text/html` без перенаправления, адресная строка браузера сохраняется. Каталог `YYMMDD/index.html` даёт `301`, файл без расширения отдаётся `application/octet-stream` и скачивается браузером, `_redirects` на GitHub Pages не применяется. Jekyll-permalink даёт тот же `200`, но требует имён постов `YYYY-MM-DD-slug.md`. Схема-кандидат — статический `YYMMDD.html` плюс `.nojekyll`; адрес второго материала дня (`YYMMDD-2`) — проверка Stage 03.
- Файлы: внешний пробный репозиторий; результаты — в `PROJECT_STATE.md`, вывод — в `ARCHITECTURE.md`, очищенные свидетельства — в `STAGE02_STEP1_EVIDENCE.md`.
- Решено и утверждать не требуется: вариант A (installation для управления, user access token для создания) и схема публикации статей (статический `YYMMDD.html` плюс `.nojekyll`, ссылки на `/YYMMDD`). Оставшиеся решения владельца перед реализацией: онбординг через device flow или web flow (рекомендация — device flow, см. `ARCHITECTURE.md`); режим доступа установки (все репозитории или выборочно); нужна ли операция удаления незавершённого репозитория; подтверждение `GITHUB_OWNER` как третьего секрета.
- Согласование: создание приложения и репозитория выполнялось только с явного разрешения владельца. Проверено 2026-10-13 [П]: создание и установка приложения программно невозможны (OAuth-токен `gh` не даёт веб-сессии — `302` на `/login`; API установки в документации отсутствует), поэтому одноразовая настройка выполнена владельцем; по его разрешению пробный репозиторий создан один раз user-токеном, чтобы продолжить проверку.

### Шаг 1.1. Проверка GitHub App user access token — выполнен 2026-10-13, вариант A подтверждён

- Разведка [П]: `GET /app` по JWT → `200` (права `administration`/`contents`/`pages` — write, `metadata` — read; `client_secret` через API не отдаётся); `POST /login/device/code` → `400 device_flow_disabled` — device flow был выключен.
- Владелец включил **Enable Device Flow**; официальный device flow выдал **user access token** типа `ghu_` (не installation `ghs_`, не OAuth `gho_`), владелец `tmksdm`, срок 8 ч; выдан **refresh-токен** `ghr_` (~182 дня) с подтверждённой одноразовой ротацией.
- `POST /user/repos` этим токеном → `201`: репозиторий создан; заголовок `x-accepted-github-permissions: administration=write; repository_creation=write`. Способность user access token создавать репозиторий подтверждена.
- Инцидент: проверка «невалидным телом» оказалась небезопасной — GitHub нормализовал имя и создал публичный пустой репозиторий `tmksdm/folio-probe-name-with-spaces-` (без коммитов и Pages). Ограничение «не создавать репозитории» нарушено неумышленно одним репозиторием; его удаление — решение владельца. Вывод для реализации: имя репозитория нужно валидировать строго заранее.
- **Статус варианта A: подтверждён живой проверкой** (2026-10-13), ожидает независимого ревью.

### Шаг 2. Серверный клиент GitHub API

- Что: конфигурация интеграции; JWT (RS256, PKCS#8) и выпуск installation-токена; выбор установки по `GITHUB_OWNER`; чтение списка репозиториев с пагинацией и `repository_selection`; отображение ошибок (`401`, `403`, `404`, `409`, `422`, `429`, `5xx`, таймаут) на понятные коды; запрет логирования секретов и тел.
- Файлы: новый `src/github.js`; конфигурация рядом с `authConfig`; `.dev.vars.example`; `tests/github.test.js`.
- Проверка: тесты на настоящей криптографии (локально сгенерированная пара ключей) с подменённой сетью: claim'ы JWT, выпуск и переиспользование токена, истечение, отсутствие и несколько установок, `401`/`403`/`429`, пагинация и её предел. Закрытый маршрут `/api/github/status` под сессией показывает приложение, аккаунт установки, права, `repository_selection` и остаток лимита.
- Риск: живой GitHub уже подтвердил права установки (шаг 1); остаётся непроверенным поведение при выборочном доступе к репозиториям и при отзыве прав.

### Шаг 2.1. Подключение владельца и хранение user-токена

- Что: однократное подключение владельца через **device flow** (рекомендация; сравнение с web flow — в `ARCHITECTURE.md`); хранение пары access/refresh в существующем Durable Object `owner-auth-v1` (строка `github-tokens`, без новой БД); **single-flight ротация** refresh-токена: одновременно не более одного обмена, обмен вне транзакции, метка `rotation_started_at` **без истечения** (метка есть ⟺ новая пара не сохранена), запись новой пары и снятие метки — одной атомарной транзакцией. Любая неопределённость (потерянный ответ, перезапуск объекта с меткой, ошибка записи, `invalid_grant`) → «требуется повторное подключение», без автоматического повтора; прежний access-токен используется, пока действителен.
- Файлы: `src/github.js`, расширение `src/auth-store.js` и конфигурации, маршруты в `src/worker.js`, тесты.
- Проверка (см. тест-план в `ARCHITECTURE.md`): получение user-токена на подменённой сети; **одновременные запросы** — обмен ровно один раз; **устаревшая метка** не запускает новый обмен; **перезапуск Durable Object во время обмена** → повторное подключение; **потерянный ответ** → повторное подключение, прежний access-токен ещё работает; **ошибка записи новой пары** → обновление не считается успешным; **отзыв refresh-токена**; **повторное подключение владельца**; токены не попадают в ответы, браузер и логи.
- Риск: живой GitHub подтвердил выдачу `ghu_`-токена и ротацию (шаг 1.1); потеря ответа или перезапуск объекта во время обмена требуют повторного подключения — гарантий автоматического восстановления нет.

### Шаг 3. Проверка имени и безопасное восстановление незавершённого создания

- Что: **строгая проверка имени локально, до любого обращения к GitHub** (только `[a-z0-9-]`, длина 1–39, без краевых `-`, зарезервированные имена; GitHub нормализует «невалидные» имена и создаёт репозиторий — инцидент шага 1.1); решение по четырём случаям: (A) создан Folio и есть проверенный `folio.json` → досоздаём только отсутствующее; (B) репозиторий есть, `folio.json` нет → автоматических записей нет, только явное подтверждение владельца; (C) ошибка или потерянный ответ при создании → обязательное перечитывание, создание не считается успешным без него; (D) имя занято посторонним → `name_taken`, ничего не пишем. Признаки «имя/описание/тема» права не дают; существующие файлы не перезаписываются; `folio-cms` и `<owner>.github.io` не трогаются никогда; удаление репозитория в интерфейсе отсутствует.
- Файлы: новый `src/sites.js`, маршруты в `src/worker.js`, расширение `tests/worker.test.js`.
- Проверка (см. тест-план в `ARCHITECTURE.md`): создание с нуля; **потерянный ответ при создании репозитория** → перечитывание и решение по фактическому содержимому; **занятое имя** → `name_taken` без записи; повторный запрос после сбоя на каждом шаге (после репозитория, файлов, темы); потерянный ответ и таймаут; два одновременных запроса на одно имя; повреждённый `folio.json`; репозиторий с описанием и темой без `folio.json` (запись запрещена до подтверждения); проверка, что подтверждение не открывает доступ к репозиториям из чёрного списка; регресс на инцидент — имя с пробелами в GitHub не отправляется.
- Риск: сценарии «репозиторий недоступен приложению» и «Pages не включаются с первого раза» воспроизводятся только на живом GitHub.

### Шаг 4. Список сайтов, статус публикации и интерфейс

- Что: `GET /api/sites` — репозитории установки с темой `folio-site`, из которых показываются только проверенные по `folio.json`; `GET /api/sites/<name>/status` — проверка публикации (`building`/`built`/`errored` плюс реальный `200` и метка страницы); панель «Сайты» с формой создания, состояниями, подтверждением, повтором и ссылкой на сайт.
- Файлы: `src/worker.js`, `src/ui.js`, `tests/preview-server.js`, `tests/fixtures.js`, `tests/browser-check.js`.
- Проверка: браузерный сценарий на HTTPS-стенде с подменённым GitHub — создание, «публикуется», «опубликован», занятое имя, ошибка сети и повтор, «требует подтверждения» с кнопкой подтверждения, проверка статуса по кнопке; ширины 1440/390/320 без горизонтальной прокрутки, клавиатура.
- Риск: подмена GitHub в стенде не доказывает реальную публикацию — это отдельная ручная проверка владельца.

### Шаг 5. Развёртывание и ручная приёмка владельцем

- Что: раздел в `DEPLOY.md` — создание GitHub App, включение device flow, доступ ко всем репозиториям, конвертация ключа, три секрета; однократное подключение владельца; владелец публикует и создаёт первый сайт с телефона.
- Файлы: `DEPLOY.md`, `PROJECT_STATE.md`.
- Проверка: сайт открывается по `https://tmksdm.github.io/<name>`; повторные нажатия не создают второй репозиторий; отличия `repository_selection` и поведение при отзыве прав проверены на живом аккаунте.
- Риск: одноразовая настройка выполняется руками; неверный формат ключа и выборочный доступ к репозиториям ловятся понятными ошибками, но требуют внимания владельца.

## Критерии приёмки Stage 02

1. Создание репозитория подтверждено живой проверкой выбранным механизмом: измерено, что installation-токен репозиторий **не создаёт** (шаг 1), поэтому выбран вариант A; шаг 1.1 подтвердил, что GitHub App user access token типа `ghu_` от лица `tmksdm` создаёт репозиторий (`201`). **Критерий закрыт** — ожидает независимого ревью.
2. С телефона из админки создаётся сайт по имени и заголовку; адрес `https://tmksdm.github.io/<name>` открывается и отдаёт страницу созданного сайта. Публикация асинхронная: интерфейс показывает «публикуется» и даёт проверить статус повторно, гарантия «за 1–2 минуты» не требуется.
3. Владелец не выполняет ручных действий в GitHub при создании сайта: одноразово — настройка приложения и подключение (authorize), далее сайты создаются без его участия; секреты не попадают в браузер, Git и логи.
4. Повторные нажатия, перезагрузка и повтор после сбоя не создают второй репозиторий и не переписывают существующие файлы; незавершённое создание доводится до конца из админки.
5. Репозиторий без проверенного `folio.json` не изменяется автоматически: он либо получает явное подтверждение владельца, либо остаётся нетронутым; `folio-cms` и `<owner>.github.io` не изменяются никогда.
6. Минимум два сайта работают независимо: у каждого свой репозиторий, адрес и история; сбой одного не влияет на другой.
7. Все новые маршруты требуют серверную сессию; анонимные получают `401` или `303` на вход, как сейчас.
8. Сбои и лимиты GitHub (таймаут, `401`, `403`, `429`, `5xx`) дают понятную ошибку и никогда — молчаливый успех; различаются «не создан», «создан, публикуется», «опубликован» и «статус неизвестен».
9. Традиционной базы данных нет: список сайтов и состояние выводятся из GitHub; единственный Durable Object остаётся хранилищем авторизации.
10. `npm run check`, `npm test`, `npm run build` проходят; браузерный сценарий на локальном стенде проходит.
11. Вопрос адресов статей закрыт измерением на своём Pages (схема-кандидат `YYMMDD.html` плюс `.nojekyll` отдаёт `/YYMMDD` как `200 text/html` без перенаправления) и явным решением владельца — до начала Stage 03; адреса второго материала дня (`YYMMDD-2`) проверяются в Stage 03.
