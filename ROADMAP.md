# Этапы

Каждый этап заканчивается проверками, коммитом в GitHub и остановкой для внешнего ревью. По указанию пользователя от 2026-10-11 результат публикуется прямо в `main`. Следующий этап требует явного одобрения. Старая дорожная карта Stage 00 отменена.

| Этап | Один результат | Статус |
|---|---|---|
| 01 — Первая работающая админка | Собственный адаптивный интерфейс; Cloudflare Workers; собственный email-код через Resend; Turnstile; SQLite Durable Object; защищённая сессия | Принят владельцем, коммит `7b26ddd` |
| 02 — Создание сайтов | Создание независимых сайтов из админки; автоматическое создание GitHub-репозиториев и настройка Pages; несколько сайтов; ссылки `https://tmksdm.github.io/site-name` | План уточнён после ревью 2026-10-12, ожидает повторного ревью |
| 03 — Редактор и публикация | Создание, редактирование, удаление Markdown-статей; изображения; черновики и публикация; автоматические постоянные `/YYMMDD`, `/YYMMDD-2` и далее; GitHub API без ручных коммитов | Не разрешён |
| 04 — Публичный сайт | Минималистичный адаптивный дизайн; название и список статей; полнотекстовый поиск; пагинация; светлая/тёмная темы; корректные статьи и изображения | Не разрешён |
| 05 — Доводка | Резервное копирование и восстановление; безопасность; телефон и компьютер; исправления и финальная документация | Не разрешён |

Этапы 03–05 не разрешены к реализации.

## Обязательные границы

- `tmksdm/folio-cms` — только движок и админка. Все публичные сайты — в отдельных репозиториях на GitHub Pages, несколько независимых сайтов из одной панели.
- Полноценное повседневное использование с телефона, без ручной работы владельца с GitHub.
- Ссылки на главную — без завершающего слеша; допускается перенаправление GitHub Pages на корень со слешем.
- Статьи — без `.html` и завершающего слеша; требование сохраняется, совместимость проверяется экспериментом (шаг 1). Если Pages не поддерживает требование, остановиться и согласовать решение с владельцем.
- Без традиционной БД контента, обязательных платных сервисов, секретов в браузере и публичных репозиториях. Будущие требования учитывать без преждевременной реализации.

## Stage 02 — план реализации

Техническое обоснование, права по вызовам, правила принадлежности репозитория и разбор сбоев — в `ARCHITECTURE.md`, раздел «Stage 02: создание сайтов».

### Шаг 1. Адреса статей на своём GitHub Pages (решение владельца)

- Что: пробный публичный репозиторий с `index.html`, каталогом `a/index.html`, файлом `b.html`, файлом без расширения `c`, `.nojekyll`, `404.html` и `_redirects`; измерения curl и в браузере по таблице из `ARCHITECTURE.md`, включая Jekyll-пост `/YYMMDD` и ветку без `.nojekyll`.
- Файлы: внешний пробный репозиторий; результаты — в `PROJECT_STATE.md`, вывод — в `ARCHITECTURE.md`.
- Проверка: таблица фактических статусов, `Location`, `Content-Type` и итогового адреса в адресной строке вместо предположений.
- Риск: требование может оказаться невыполнимым в точном виде. Тогда решение принимает владелец: принять `301` (адрес для набора и пересылки не меняется, финальный адрес получает слеш) или изменить требование. Вариант с `404.html` как механизмом публикации статей не применяется без отдельного решения.
- Согласование: создание репозитория — только с явного разрешения владельца. Эксперимент не запускался.

### Шаг 2. Серверный клиент GitHub API

- Что: конфигурация интеграции; JWT (RS256, PKCS#8) и выпуск installation-токена; выбор установки по `GITHUB_OWNER`; чтение списка репозиториев с пагинацией и `repository_selection`; отображение ошибок (`401`, `403`, `404`, `409`, `422`, `429`, `5xx`, таймаут) на понятные коды; запрет логирования секретов и тел.
- Файлы: новый `src/github.js`; конфигурация рядом с `authConfig`; `.dev.vars.example`; `tests/github.test.js`.
- Проверка: тесты на настоящей криптографии (локально сгенерированная пара ключей) с подменённой сетью: claim'ы JWT, выпуск и переиспользование токена, истечение, отсутствие/несколько установок, `401`/`403`/`429`, пагинация и её предел. Закрытый маршрут `/api/github/status` под сессией показывает приложение, аккаунт установки, права, `repository_selection` и остаток лимита.
- Риск: реальные права установки и доступность созданного репозитория проверяются только на живом GitHub (шаг 5); до этого поведение подтверждено тестами и документацией.

### Шаг 3. Принадлежность и сходимость создания сайта

- Что: маркеры (описание `Folio site: …`, тема `folio-site`, `folio.json` с `managedBy`), правила «свой / завершён / чужой», досоздание существующего сайта, отказ на чужой репозиторий, запрет перезаписи существующих файлов, объединение тем, включение Pages без изменения чужих настроек.
- Файлы: новый `src/sites.js`, маршруты в `src/worker.js`, расширение `tests/worker.test.js`.
- Проверка: тесты со стендом GitHub — создание с нуля; повторный запрос после сбоя на каждом шаге (после создания репозитория, после файлов, после темы); потерянный ответ и таймаут; два одновременных запроса на одно имя; занятое имя чужого репозитория (`folio-cms`, `<owner>.github.io`); повреждённый `folio.json`; недоступный новому приложению репозиторий (`403`); проверка, что повтор не создаёт второй репозиторий и не переписывает файлы.
- Риск: сценарии «недоступен созданный репозиторий» и «Pages не включаются с первого раза» воспроизводятся только на живом GitHub.

### Шаг 4. Список сайтов, статус публикации и интерфейс

- Что: `GET /api/sites` — список из установки с фильтром по теме и состоянием «завершён / не завершён»; `GET /api/sites/<name>/status` — проверка публикации (`building`/`built`/`errored` плюс реальный `200` и метка страницы); панель «Сайты» с формой создания, состояниями, повтором и ссылкой на сайт.
- Файлы: `src/worker.js`, `src/ui.js`, `tests/preview-server.js`, `tests/fixtures.js`, `tests/browser-check.js`.
- Проверка: браузерный сценарий на HTTPS-стенде с подменённым GitHub — создание, «публикуется», «опубликован», занятое имя, ошибка сети и повтор, «не завершён» с кнопкой «Завершить», проверка статуса по кнопке; ширины 1440/390/320 без горизонтальной прокрутки, клавиатура.
- Риск: подмена GitHub в стенде не доказывает реальную публикацию — это отдельная ручная проверка владельца.

### Шаг 5. Развёртывание и ручная приёмка владельцем

- Что: раздел в `DEPLOY.md` — создание GitHub App, выбор доступа ко всем репозиториям, конвертация ключа, три новых секрета; владелец публикует и создаёт первый сайт с телефона.
- Файлы: `DEPLOY.md`, `PROJECT_STATE.md`.
- Проверка: сайт открывается по `https://tmksdm.github.io/<name>`; повторные нажатия не создают второй репозиторий; отличия `repository_selection` и поведение при отзыве прав проверены на живом аккаунте.
- Риск: одноразовая настройка выполняется руками; неверный формат ключа и выборочный доступ к репозиториям ловятся понятными ошибками, но требуют внимания владельца.

## Критерии приёмки Stage 02

1. С телефона из админки создаётся сайт по имени и заголовку; адрес `https://tmksdm.github.io/<name>` открывается и отдаёт страницу созданного сайта. Публикация асинхронная: интерфейс показывает «публикуется» и даёт проверить статус повторно, гарантия «за 1–2 минуты» не требуется.
2. Владелец не выполняет ручных действий в GitHub при создании сайта (кроме одноразовой настройки приложения); секреты не попадают в браузер, Git и логи.
3. Повторные нажатия, перезагрузка и повтор после сбоя не создают второй репозиторий и не переписывают существующие файлы; незавершённое создание доводится до конца из админки.
4. Занятое имя без маркеров Folio (в том числе `folio-cms` и `<owner>.github.io`) даёт понятное сообщение, чужой репозиторий не изменяется.
5. Минимум два сайта работают независимо: у каждого свой репозиторий, адрес и история; сбой одного не влияет на другой.
6. Все новые маршруты требуют серверную сессию; анонимные получают `401` или `303` на вход, как сейчас.
7. Сбои и лимиты GitHub (таймаут, `401`, `403`, `429`, `5xx`) дают понятную ошибку и никогда — молчаливый успех; различаются «не создан», «создан, публикуется», «опубликован» и «статус неизвестен».
8. Традиционной базы данных нет: список сайтов и состояние выводятся из GitHub; единственный Durable Object остаётся хранилищем авторизации.
9. `npm run check`, `npm test`, `npm run build` проходят; браузерный сценарий на локальном стенде проходит.
10. Вопрос адресов статей закрыт экспериментом на своём Pages и явным решением владельца — до начала Stage 03.
